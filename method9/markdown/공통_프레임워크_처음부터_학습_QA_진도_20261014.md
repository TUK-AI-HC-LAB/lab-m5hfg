## 학습 목표와 중점

목표는 method 내부 알고리즘을 제외한 공통 프레임워크를 실제 호출 순서로 설명하는 것이다. 파일 이름이나 함수 역할을 외우는 데서 그치지 않고, 한 실행 설정이 어떻게 객체·데이터·결과로 이어지는지 추적한다.

각 청크에서 설명할 내용은 다음과 같다.

- 현재 파일과 함수, 그 파일이 대표적으로 담당하는 일.
- 호출한 위치와 다음 함수로 넘어가는 이유.
- 입력 변수의 이름·자료형·구체적인 값.
- 실제 실행되는 줄과 아직 실행하지 않는 함수 정의.
- 값 저장·참조·클래스 조회·객체 생성·기능 실행의 차이.
- 반환값의 자료형과 반환 후 연결되는 변수.
- 정상 경로와 조건 분기·오류 경로.
- 기존 동작과 실제 보완 내용, 미적용 후보의 구분.

Python의 기본 문법도 실제 코드에서 만나는 순서대로 함께 익힌다.

## 사용자가 정한 설명 방식

- 맨 처음 진입점부터 시작한다.
- 함수를 호출하면 내부 본문을 따라가고, 반환 후 호출한 위치로 돌아온다.
- 다른 `.py`로 넘어갈 때 파일의 대표 역할과 이동 이유를 설명한다. 실제 파일이 이동하는 것이 아니라 실행 흐름이 다른 함수로 넘어간다는 뜻이다.
- 함수 선언의 타입 힌트도 생략하지 않는다.
- 실제 변수명을 그대로 사용한다. 혼동을 일으키는 축약명을 새로 만들지 않는다.
- 내부 함수를 설명 없이 생략한 채 다음 파일로 넘어가지 않는다.
- 함수 설명이 끝나면 번호·표 없이 짧은 화살표 흐름 요약을 붙인다.
- 질문에 대한 설명을 마친 뒤 모범답안을 제시한다.
- 이미 이해한 부분은 반복 질문을 줄이고 다음 청크로 넘어간다.

흐름 요약 형식의 예:

```text
입력 설정 딕셔너리
→ 이름 변경·자료형 통일
→ 정리된 딕셔너리 반환
→ resolve_args()로 복귀해 experiment에 연결
```

## 현재 진도

### 설명을 완료한 구간

`main.py`의 진입점, `main()`의 로그 설정, `resolve_args()`의 전체 설정 처리, 설정 로그 출력과 W&B 분기까지 설명했다.

`main_dataset.py`의 `dataset(args)`가 내부 함수 객체를 반환하는 구조를 설명했다. 이후 사용자의 요청으로 그 내부 `get_dataloaders()`도 앞부분부터 정독했다.

범주 그룹 처리, `resolve_dataset_plan()`, Dataset 전용 이름 선택, registry 등록 정보 조회, 생성 함수 선택, `_build_path_datasets()`의 클래스·split 조회와 공통 인자 준비, 이상 생성용 경로 기본값, 학습 Dataset 생성 호출의 인자까지 설명했다.

### 설명 중인 정확한 위치

일반 MVTec 경로를 기준으로 `dataset_class(...)` 호출에서 `datasets/base.py`의 `BaseDataset.__init__()`에 들어온 상태다.

```python
super().__init__()
self.root = self.source = source
self.split = split
self.train_val_split = train_val_split
self.seed = kwargs.get("seed", 0)
```

### 실행 순서와 학습 순서를 구분할 것

실제 `dataset(args)` 호출은 `get_dataloaders`를 정의하고 반환할 뿐, 그 내부를 즉시 실행하지 않는다. 실제 실행에서는 `net(args)` 준비 후 `main_run.py`의 runner가 `get_dataloaders(0)`를 호출한다.

현재 학습은 사용자가 Dataset 코드를 먼저 완전히 보자고 요청하여 내부 함수를 미리 펼쳐 읽는 중이다. 그러므로 정독한 순서를 실제 실행 순서로 그대로 설명하면 안 된다.

### 이 정독에서 아직 남은 구간

- `BaseDataset.__init__()`의 나머지 속성 저장·파일 목록 구성·전처리 준비.
- 이미지·mask 경로 목록 생성과 학습·검증 분할의 내부 코드.
- validation/test Dataset 생성, 구조 검사, DataLoader 생성 및 반환.
- `net(args)`와 그 내부 보조 함수·Trainer 생성 과정의 상세 정독.
- `main_run.py`의 실행 준비·범주/seed 반복·Trainer 호출·결과 수집.
- 샘플 요청·배치 구성·장치 이동·출력·후처리·평가·CSV 저장의 전체 연결.

위 부분 중 일부는 이전 대화에서 개념을 배웠지만, 이번 “처음부터 호출 순서대로” 정독을 완료한 것으로 기록하지 않는다.

## Q&A — 프로그램 시작과 설정

### 처음 어떤 함수가 실행되고, 왜 실행되는가?

Python은 파일의 최상위 코드를 위에서 아래로 실행한다. import 과정의 코드도 먼저 실행될 수 있으므로 `main()`이 모든 Python 호출 중 최초라고 단정하지 않는다. 프레임워크 본 실행의 진입점은 다음 코드다.

```python
if __name__ == "__main__":
    raise SystemExit(main(sys.argv[1:]))
```

직접 실행하면 조건이 참이 되어 `main()`을 호출한다. method 옵션이 `main()` 호출 여부를 결정하는 것은 아니다. `main()`이 완료된 뒤 반환한 종료 코드로 프로그램을 종료한다.

사용자는 `main()`이 설정을 합쳐 다른 파일에 전달하며 전체 실행을 연결한다는 목적을 설명했다. “method를 실행해서 main이 시작된다”는 표현은 “main.py를 직접 실행해서 진입점이 main을 호출한다”로 정정했다.

### 파일명을 제외한 명령 인자는 기본 설정을 가져오는가?

아니다. `sys.argv[1:]`는 실행 파일명만 제외한 명령 인자 문자열 목록이다. method도 포함된다. 기본값과 YAML은 이후 읽는다.

```python
# 설명용 실행: python main.py --method patchcore --batch-size 8
sys.argv[1:]
# ["--method", "patchcore", "--batch-size", "8"]
```

`python`은 해당 목록에 포함되지 않는다. 숫자도 이 단계에서는 문자열이다. CLI 옵션의 실제 표기는 `--batch-size`이며, 이전 설명 중 사용한 `--batch_size` 예시는 그대로 실행하지 않는다.

### args에 설정이 모두 결합되는가?

`resolve_args()`가 공통 기본값 → method YAML → experiment YAML → CLI 순서로 결합한다. 같은 키는 나중 값이 덮어쓴다. CLI에 없는 항목은 앞에서 정한 값이 유지된다. 이 객체에 이미지나 Trainer가 자동으로 포함되는 것은 아니다.

사용자는 method 설정 8, experiment 설정 4, CLI 미지정인 `batch_size`의 최종값을 `4`로 답했다.

### SimpleNamespace는 무엇이며, 그 안에 args가 있는가?

이름 붙인 속성으로 값을 담는 객체다. `SimpleNamespace(**values)`는 딕셔너리 항목을 속성으로 담은 객체를 만든다. `args`는 반환된 객체를 가리키는 변수명이다. 객체 안에 `args`라는 속성이 자동으로 생기는 것은 아니다.

```python
args.batch_size
```

처럼 읽는다. 설정을 결합하는 기능은 앞의 코드가 수행하고, `SimpleNamespace`는 결과를 담는다.

### resolve_args 호출 후 어디로 돌아오는가?

`argv`를 받아 함수 본문을 실행하고 최종 객체를 반환한다. 호출했던 `main()`의 `args = resolve_args(argv)`로 돌아와 반환 객체를 `args`에 연결한 뒤 다음 줄을 실행한다. 두 함수는 같은 `main.py`에 있다.

### build_parser와 parse_args의 차이는?

`build_parser()`는 옵션 이름·자료형·기본값·허용값 등의 해석 규칙을 등록한다. 실제 인자 해석은 `parser.parse_args(argv)`가 수행한다. 결과 `parsed`는 `argparse.Namespace`이며 최종 `args`와는 다른 단계의 객체다.

### CLI에 dataset이 없으면 Dataset을 사용할 수 없는가?

아니다. 이후 experiment YAML과 기본값으로 결정할 수 있다. 사용자가 이 점을 맞게 답했다. `None`인 CLI 항목은 `cli_values`에서 제외하여 기존 설정을 덮지 않는다.

### config_path가 없으면 load_yaml이 실행되는가?

경로가 존재하지 않으면 `experiment = {}`로 두고 `load_yaml()`과 `_normalise_experiment()`을 모두 건너뛴다. 사용자가 이 조건과 호출·반환 흐름을 설명했다.

`cli_values.pop("config")`는 경로를 반환하면서 해당 딕셔너리 항목만 제거한다. 파일을 삭제하지 않는다.

### YAML의 seeds: 3은 어떤 자료형인가?

정수다. 사용자가 정수라고 답했다. `load_yaml()`은 YAML을 Python 값으로 해석하고, 전체 설정이 딕셔너리인지 검사한 뒤 반환한다.

### method와 mainmodel을 동시에 적으면?

`_normalise_experiment()`가 별칭을 내부 이름으로 변경하기 전에 중복을 검사한다. 둘 다 있으면 값이 같아도 오류를 발생시킨다. 사용자가 오류 발생 이유를 설명했다.

### 이미 리스트인 범주를 다시 리스트로 감싸는가?

아니다. 문자열 범주만 `[문자열]`로, 정수 seed만 `[정수]`로 감싼다. 기존 리스트는 유지한다. 사용자가 문자열일 때만 실행된다고 답했다.

### CLI에 method가 없고 experiment가 simplenet이면?

experiment 값을 사용한다. 사용자가 `simplenet`이라고 답했다. 다만 이 답은 대화에서 제시한 가정의 우선순위 설명이다. 실제 실행에서는 이후 registry의 허용 이름 검사를 통과해야 하며, 저장된 코드의 SimpleNet method 키는 `simple`이다. `simplenet`을 검증된 실행 명령으로 사용하면 안 된다.

### method YAML이 없어서 {}를 반환하면 기본값을 지우는가?

아니다. `values.update({})`는 변경할 항목이 없으므로 기존 값을 유지한다. 사용자가 그대로 유지한다고 답했다.

### data_path의 값이 있으면 실제 경로도 유효한가?

`if not values.get("data_path")`는 값이 비어 있는지만 검사한다. 존재하지 않는 폴더의 비어 있지 않은 문자열도 통과할 수 있다. 사용자가 이 검사만으로 오류를 잡을 수 없다고 답했다.

설정 처리 요약:

```text
명령 인자
→ 해석 규칙 준비·CLI 해석
→ experiment 읽기·별칭과 자료형 정리
→ method 선택·검사
→ 기본값·method YAML·experiment·CLI 결합
→ 필수 설정 검사
→ SimpleNamespace 반환·main의 args에 연결
```

## Q&A — 로그와 실험 기록

### logging은 함수인가?

`logging`은 Python 표준 모듈이다. 실제 호출은 `logging.basicConfig(level=logging.INFO)`이며 로그 설정을 준비한다. 모델을 실행하지 않는다. 이후 `logger.info()`는 이 코드에서 별도로 가져온 Loguru 기능이다.

### vars()는 무엇인가?

객체의 속성 딕셔너리를 가져오는 내장 함수다. `vars(args)`로 설정을 W&B에 전달한다. 독립적인 복사본을 만드는 함수는 아니다.

### wandb는 무엇을 기록하며, 어디에 기록하는가?

현재 코드에서는 실험 설정과 지표 기록에 사용한다. `wandb.init()`은 기록 세션을 시작하며, 결과 기록은 이후 `wandb.log()`로 수행한다. init 호출만으로 모든 결과가 자동 기록되는 것은 아니다.

일반적인 온라인 모드에서는 W&B 프로젝트로 동기화하며, 오프라인 모드에서는 로컬 기록을 나중에 동기화할 수 있다. 이 대화에서는 현재 계정·모드·정확한 로컬 기록 위치를 확인하지 않았다. GitHub에 자동 저장되는 것은 아니다.

### CLI에서는 wan으로 지정하는가?

내부 속성은 `args.wan`, CLI 옵션은 `--enable-wandb`다. 옵션을 넣으면 `True`가 된다. 미지정이면 YAML·기본값을 사용하며 공통 기본값은 `False`다.

사용자는 `wan=False`여도 전체 프레임워크는 실행하고 W&B 초기화만 건너뛴다고 답했다.

## Q&A — Dataset 구성과 registry

### dataset(args)가 바로 DataLoader를 만드는가?

아니다. `("get_dataloaders", get_dataloaders)`를 반환한다. 첫 항목은 이름 문자열, 둘째는 나중에 호출할 함수 객체다. 사용자가 나중에 DataLoader를 만들 함수라고 답했다. 괄호 없는 함수 참조와 함수 호출을 구분했다.

### bottle+cable은 어떻게 처리되는가?

`raw_group.split("+")` 결과를 튜플로 만든다. 사용자는 첫 그룹 `"bottle+cable"`이 `("bottle", "cable")`이 된다고 설명했다.

`["bottle", "cable"]`은 별도 그룹 두 개, `["bottle+cable"]`은 합친 그룹 하나다.

### resolve_dataset_plan이 끝나면 이미지를 읽었는가?

아니다. Dataset 이름·루트 경로·범주를 `DatasetPlan`에 저장했을 뿐이다. 사용자가 아직 이미지가 아니라 경로 정보를 저장한 단계라고 답했다. 동일 루트 경로를 세 split에 전달해도 실제 이미지 목록이 동일하다는 의미는 아니다.

### resolve_dataset_name의 반환값은?

전용 등록 여부를 보고 Dataset 구현 이름 문자열을 반환한다. 사용자는 MVTec과 AnomalyCLIP 조합에서 `"mvtec_anomalyclip"`이라는 문자열이라고 답했다. `args.dataset`을 직접 변경하거나 Dataset 객체를 생성하지 않는다.

### Mapping[str, Any], key: str, component_name: str, -> Any는?

`_get_spec()` 선언의 타입 힌트다. 문자열 키로 조회할 수 있는 대응 구조, 조회 이름 문자열, 오류 메시지용 종류 문자열을 입력받으며 반환 타입을 특정하지 않는다. 타입 힌트 자체는 자동 형변환·실행 중 검사를 수행하지 않는다.

### DATASET_REGISTRY는 어디에 무엇을 담는가?

`component_registry.py`에 정의된 실제 딕셔너리다. 문자열 Dataset 이름을 키로 하고, 값에는 `DatasetSpec` 객체를 담는다. 각 spec에는 모듈 이름·클래스 이름·생성 방식이 있다. 이미지·데이터 경로·실제 Dataset 객체를 담는 곳은 아니다.

`DatasetSpec` 조회, 클래스 가져오기, Dataset 객체 생성은 서로 다른 단계다.

### builder에 함수를 연결하면 Dataset이 만들어지는가?

아니다. `_DATASET_BUILDERS[spec.constructor_style]`로 생성 함수를 선택한다. `builder(...)`를 호출할 때 생성 절차가 실행된다. 사용자가 함수를 선택한 상태라고 답했다.

### spec.load_class()의 반환값은?

등록된 모듈을 가져오고 클래스 이름으로 조회·검사한 뒤 클래스 자체를 반환한다. 사용자가 설계도인 클래스라고 답했다. `self`는 호출한 spec 객체이고 `-> Type[Any]`는 클래스 반환을 뜻하는 타입 힌트다.

### spec.load_split()이 데이터를 나누는가?

아니다. 모듈의 `DatasetSplit` 클래스를 반환한다. 사용자가 분할 종류를 지정할 클래스를 가져온다고 답했다. `split.TRAIN`은 Enum 멤버이며 문자열 `"train"` 자체와는 구분한다.

### common["args"]는 복사한 객체인가?

기존 `args` 객체다. `_common_dataset_kwargs()`는 resize·imagesize·args를 딕셔너리로 묶는다. 사용자가 기존 객체라고 답했다. 이후 `**common`으로 생성자에 펼쳐 전달한다.

### anomaly_source_path가 빈 문자열이면?

`getattr(args, "anomaly_source_path", "") or "/datasets/dtd/images"`에 따라 기본 경로 문자열을 사용한다. 사용자가 `"/datasets/dtd/images"`라고 답했다. 이 줄은 데이터 읽기나 경로 존재 검사가 아니다.

### 위치 인자와 키워드 인자는?

Dataset 생성 호출의 `plan.train_path`는 위치 인자이고 `classname=...`은 키워드 인자다. 사용자가 둘을 구분했다. 첫 경로는 생성자의 `source`로 들어간다.

### 일반 MVTec 생성자는 어느 파일에서 실행되는가?

`datasets/mvtec.py`의 `MVTecDataset`은 자체 `__init__()` 없이 `BaseDataset`을 상속한다. 따라서 공통 초기화는 `datasets/base.py`의 `BaseDataset.__init__()`에서 실행된다. AnomalyCLIP 전용 등록 등 다른 구현도 항상 같다고 일반화하지 않는다.

### **common과 **kwargs는 무엇이 다른가?

호출 쪽 `**common`은 딕셔너리를 키워드 인자로 펼친다. 생성자 선언의 `**kwargs`는 별도로 선언하지 않은 추가 키워드 인자를 딕셔너리로 모은다. seed·args 등이 kwargs에 들어간다.

Dataset 구성 학습 요약:

```text
범주 그룹 선택
→ DatasetPlan 구성
→ 전용 Dataset 이름·DatasetSpec 조회
→ 생성 함수 선택
→ Dataset 클래스·DatasetSplit 조회
→ 공통 인자·경로 준비
→ 클래스 호출
→ BaseDataset 초기화 앞부분 정독 중
```

## 현재 답변으로 확인된 것과 재확인할 것

확인된 것은 단일 질문에 대한 구분 능력이다. 사용자는 설정 우선순위, 경로 존재 검사와 값 검사, 문자열·리스트 변환, 등록 정보·클래스·객체·함수 참조의 차이, 위치·키워드 인자 등에 올바르게 답했다.

다만 단일 답변만으로 전체 호출 흐름을 혼자 완벽하게 재현할 수 있다고 보지 않는다. 다음 사항은 연결 설명으로 다시 확인할 필요가 있다.

- 각 함수 호출에서 입력을 받고, 반환값을 어느 변수에 연결하는지.
- 내부 함수 정의 시점과 실제 호출 시점의 차이.
- Dataset 생성자가 경로 목록과 전처리를 준비하는 시점, 실제 샘플 이미지를 읽는 시점의 차이.
- 선택한 Dataset 구현에 따라 생성자와 전처리가 달라질 수 있다는 점.
- 예시 이름과 실제 registry에서 허용하는 이름의 구분.

## 앞으로의 학습 방향

새로운 method를 개발하거나 성능 개선을 주장하는 단계가 아니라, 공통 프레임워크의 동작을 코드로 설명하는 기반을 다지는 방향이다.

현재 생성자 설명을 마친 뒤 Dataset·DataLoader 구성을 끝까지 따라간다. 그다음 아직 실행하지 않은 Trainer 준비와 runner를 실제 실행 순서로 다시 연결한다. 최종적으로 한 이미지가 파일 경로에서 샘플·배치·모델 출력·평가 지표·CSV로 이어지는 흐름을 설명할 수 있어야 한다.

종합 확인에서는 “이 함수가 무엇을 한다”만 말하지 않고 다음처럼 설명한다.

> 어느 파일의 어느 함수에서 어떤 자료형의 입력을 받아, 어떤 객체나 값을 만들고, 무엇을 반환하여 호출한 곳의 어느 변수에 연결하는지 설명한다. 아직 실행하지 않은 단계와 실제 실행한 단계를 구분한다.

## 재개 위치

다음 학습은 `datasets/base.py`의 `BaseDataset.__init__()`에서 이어간다. 마지막 resize 기본값 질문을 확인한 후, 다음 실제 코드부터 읽는다.

```python
self.transform_std = IMAGENET_STD
self.transform_mean = IMAGENET_MEAN
self.args = kwargs['args']
```
