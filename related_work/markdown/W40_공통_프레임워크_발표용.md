# W40 발표 - 공통 이상 탐지 프레임워크와 코드 기반 개선 후보

## 발표 한 문장

> 여러 이상 탐지 방법을 같은 데이터 처리·실행·평가 흐름에서 교체할 수 있는 공통 프레임워크를 분석했고, 각 방법이 정상 기준을 만드는 방식의 차이에서 다음 연구 후보를 좁혔습니다.

---

## 1. 이번 발표의 범위

이번 발표의 주제는 특정 모델의 성능이 아니라 **공통 프레임워크의 구조**임.

공통 프레임워크는 다음을 통일함.

- 설정 읽기
- Dataset과 DataLoader
- `method`에 따른 Trainer 선택
- 실행 순서
- image score, anomaly map, metric, CSV 출력

단, 모든 방법의 내부 수식까지 같게 만드는 것은 아님. 방법마다 정상 기준과 anomaly score 계산식은 다름.

```text
공통 framework: data 처리 → model 선택 → 실행 → 결과 형식
방법별 Trainer:  정상 기준 생성 → anomaly score/map 계산
```

---

## 2. 공통 프레임워크 구조

```text
experiment YAML
  ↓
main.py: 설정 병합
  ├─ component_registry.py: method/dataset 이름 → 실제 class 연결
  ├─ main_dataset.py: Dataset → 공통 batch dict
  ├─ main_net.py: 선택된 Trainer 생성·load
  └─ main_run.py: 공통 lifecycle 실행·metric/CSV 저장
                              ↓
                    method별 Trainer.predict()
                              ↓
                 image score + anomaly map + metric
```

### 핵심 개념: registry

`method: anomalyclip`처럼 YAML에 적은 이름이 registry를 거쳐 실제 Trainer class를 선택함.

| method | Trainer 내부 정상/이상 기준 | 공통 출력 |
|---|---|---|
| `patchcore` | normal memory bank와 최근접 거리 | image score, anomaly map, metric |
| `simple` | discriminator가 만든 정상/가짜 이상 경계 | image score, anomaly map, metric |
| `rd` | teacher–decoder feature 복원 차이 | image score, anomaly map, metric |
| `anomalyclip` | normal/abnormal text feature 유사도 | image score, anomaly map, metric |


> runner는 각 논문의 내부 수식을 직접 알 필요가 없습니다. registry가 고른 Trainer가 공통 interface를 지키면, 같은 실행·평가 흐름에서 서로 다른 방법을 교체할 수 있습니다.

## 3. 공통 데이터 처리

### 입력 계약

Dataset은 이미지 파일 하나를 아래 dict로 만듦.

```text
{
  image:      모델 입력 RGB tensor,
  mask:       실제 결함 위치 정답,
  is_anomaly: 정상=0 / 이상=1 정답 label,
  image_path: 원본 파일 경로
}
```

DataLoader는 이 dict를 batch로 묶음. 예를 들어 AnomalyCLIP `bottle` 실행에서는 아래 shape가 확인됨.

| 값 | shape | 뜻 |
|---|---|---|
| `image` | `[1, 3, 518, 518]` | RGB 이미지 1장 |
| `mask` | `[1, 1, 518, 518]` | 결함 위치 정답 1장 |
| global feature | `[1, 768]` | 이미지 전체 특징 |
| patch feature | `[1, 1370, 768]` | 위치별 특징 1,370개 |

### 꼭 구분할 점

- `image`는 모델 입력임.
- `mask`는 모델 입력이 아니라, 모델이 만든 map을 평가하기 위한 정답임.
- image score는 사진 전체의 이상 점수 하나임.
- anomaly map은 위치별 이상 점수 지도임.

**발표에서 말할 내용:**

> 모델은 mask를 보고 결함을 찾지 않습니다. image만으로 score와 map을 만들고, mask는 나중에 위치를 맞게 찾았는지 평가할 때 씁니다.

## 4. 한 이미지 실행은 구조 검증 evidence

AnomalyCLIP adapter를 공통 framework에 연결해 MVTec AD `bottle/test/broken_large/000.png` 한 장을 실제 처리함.

![원본부터 최종 map·score까지의 실제 출력](../method6/source/results/w40_common_framework_single_image/single_image_io_panel.png)

```text
원본 PNG
  → Dataset / DataLoader
  → ImageNet 정규화 tensor
  → CLIP 정규화 tensor
  → global·patch feature
  → normal/abnormal text similarity
  → final image score + anomaly map
```

| 실제 출력 | 값 |
|---|---:|
| final image anomaly score | `0.991550` |
| final anomaly map range | `0.000272–0.969498` |
| `Trainer.predict()`와 중간 계산 score 차이 | `0.0` |

이 그림은 한 이미지의 성능을 주장하기 위한 것이 아니라, 공통 framework의 입구부터 선택된 Trainer의 출력까지 실제로 연결되었음을 보여 주는 evidence임.

## 5. 방법별 정상 기준과 코드 기반 limitation

### 5.1 PatchCore

```text
정상 train patch feature
  → coreset
  → normal memory bank
  → test patch와 최근접 거리
```

- **기준:** test patch가 정상 memory patch와 얼마나 먼가.
- **limitation:** memory를 많이 보관할수록 normal 기준은 촘촘해질 수 있지만 저장·최근접 검색 비용이 커짐.
- **현재 evidence:** coreset을 10%에서 1%로 줄이면 MVTec AD 평균 Image/Pixel AUROC가 약 `0.14%p` 낮아짐.
- **기존 개선 방향:** RD4AD는 memory bank 대신 teacher–decoder feature 복원 차이를 사용함.
- **판단:** PatchCore는 many-normal-image memory 기준선으로 유지함. 현재 few-shot extension의 직접 대상은 아님.

근거: `method1/source/patchcore_annotated/src/patchcore/patchcore.py`, `method1/source/results/PatchCore_MVTecAD_IM224_WR50_coreset_comparison.csv`.

### 5.2 RD4AD

```text
teacher feature
  ↔ reverse decoder reconstruction feature
  → feature 차이로 anomaly map
```

- **기준:** 정상 data에서 teacher feature를 decoder가 얼마나 잘 복원하는가.
- **limitation:** normal feature를 compact하게 만들고 anomaly signal을 버리도록 직접 강제하는 학습 신호가 약할 수 있음.
- **기존 개선 방향:** RD++는 optimal transport·contrast loss와 pseudo anomaly reconstruction을 추가함.
- **주의:** 현재 `transistor`의 낮은 위치 지표가 이 limitation 때문인지, annotation–prediction 위치 불일치 때문인지는 아직 구분되지 않음.

근거: `related_work/markdown/CVPR23_RDpp_Revisiting_Reverse_Distillation_for_Anomaly_Detection.md`, `meetings/2026-W34_brief.md`.

## 6. 현재 코드 기반 다음 확인

| 방법 | 다음 확인 | 이유 |
|---|---|---|
| PatchCore | coreset 비율별 실제 memory·검색 시간 측정 | 현재는 성능 변화만 있고 비용 측정값이 없음 |
| RD4AD | transistor 입력·mask·anomaly map 비교 | 낮은 위치 지표의 원인이 annotation 불일치인지 실제 feature failure인지 구분해야 함 |

현재 W40에서 주장할 수 있는 것은 framework 구조를 분석했고, PatchCore와 RD4AD에서 각기 다른 코드 기반 limitation을 확인했다는 점까지임.
