## 1. 전체 실행 흐름

데이터가 처리되는 큰 순서는 다음과 같다.

```text
실행 설정 결합
    → 데이터와 method 준비
    → Trainer의 학습·추론
    → 예측 점수와 anomaly map 후처리
    → 정답과 비교하여 지표 계산
    → 결과 정리·저장
```

실제 함수 호출에서는 준비와 실행이 나뉜다.

```text
main.py의 main()
    → resolve_args(): 최종 설정 args 생성
    → dataset(args): DataLoader를 만들 함수 준비
    → net(args): Trainer들을 만들 함수 준비
    → main_run.py의 run(): 준비한 함수를 호출하고 실험 실행
```

`dataset(args)`를 호출했다고 그 자리에서 모든 이미지를 읽는 것은 아니다. `net(args)`를 호출했다고 바로 이미지 추론을 수행하는 것도 아니다. 두 함수는 나중에 runner가 사용할 함수를 반환한다.

또한 “학습 → 추론 → 후처리 → 평가”는 계산의 흐름이다. 이 단계들이 모두 runner에 독립된 함수 호출로 나란히 적혀 있는 것은 아니다. 선택한 Trainer의 내부에서 추론과 평가를 호출할 수 있다.

## 2. main: 실행 설정을 하나의 args로 결합

### 2.1 시작점

실행 파일을 직접 실행하면 `if __name__ == "__main__":` 아래에서 `main(sys.argv[1:])`을 호출한다. `sys.argv[1:]`은 실행 파일 이름을 제외한 명령행 인자다.

`main()`은 설정을 확정하고, 필요한 구성 요소를 준비한 뒤, 전체 실행을 runner에 넘기는 진입점이다. 모델의 특징 추출이나 이상 점수 계산을 직접 담당하지는 않는다.

### 2.2 resolve_args()의 설정 병합

`resolve_args()`는 명령행 인자를 읽고, 실험 YAML을 불러온 뒤, 사용할 method를 결정한다. 이후 다음 순서로 설정을 덮어쓴다.

```text
공통 기본값 → method별 YAML → 실험 YAML → CLI에서 직접 지정한 값
```

같은 항목이 여러 곳에 있으면 오른쪽 값이 최종값이다. CLI를 먼저 읽어도 설정에 반영하는 순서는 마지막이므로 우선순위가 가장 높다.

예를 들어 공통 기본값의 `batch_size`가 8이고 실험 YAML에서 4, CLI에서 2를 지정했다면 최종값은 2다. 이 숫자는 우선순위 설명을 위한 예시다.

실험 YAML의 `method`, `category`, `seeds` 같은 이름은 내부에서 사용하는 `mainmodel`, `subdatasets`, `seed_list`로 정리한다. 여러 범주와 여러 seed를 반복할 수 있도록 단일 값도 필요한 경우 리스트로 정리한다.

### 2.3 args는 무엇인가

최종 설정 딕셔너리는 `SimpleNamespace(**values)`로 변환되어 반환된다. 이 반환 객체를 `args`에 연결한다.

```python
args.mainmodel
args.dataset
args.subdatasets
args.batch_size
```

`SimpleNamespace`는 설정값을 점 표기법으로 꺼낼 수 있게 해 주는 객체다. 그 안에 별도의 `args`가 들어 있는 것이 아니라, 만들어진 객체에 붙인 변수 이름이 `args`다.

여기까지는 실행 조건을 확정한 단계다. 데이터 경로 문자열이 있다는 확인과 그 경로에 실제 파일이 있다는 확인도 서로 다르다.

> 흐름 요약: 명령행·YAML·기본값을 읽음 → 우선순위대로 결합 → 최종 설정 객체 args 반환.

## 3. dataset: Dataset 선택과 DataLoader 구성

### 3.1 dataset(args)가 준비하는 것

`main_dataset.py`의 `dataset(args)`는 다음 두 값을 묶어서 반환한다.

```python
("get_dataloaders", get_dataloaders)
```

앞의 문자열은 runner가 함수를 찾는 이름이고, 뒤의 값은 함수 자체다. 아직 `get_dataloaders()`를 실행한 것은 아니다.

runner가 이 함수를 호출하면 `args.subdatasets`의 범주별로 Dataset과 DataLoader를 만든다. `"bottle+cable"`처럼 묶인 항목은 두 범주를 하나의 실험 단위로 처리한다.

### 3.2 registry에서 Dataset을 선택하는 이유

설정에 적힌 `"mvtec"` 같은 문자열만으로는 이미지를 읽을 수 없다. 이 이름에 대응하는 실제 Dataset 클래스를 찾아야 한다.

registry는 등록된 이름을 클래스의 모듈 위치, 클래스 이름, 생성 방식 등의 정보와 연결한다. 등록 정보를 가져오는 것, 클래스를 불러오는 것, 그 클래스로 Dataset 객체를 만드는 것은 서로 다른 단계다.

같은 데이터셋도 method에 따라 다른 Dataset 구현을 선택할 수 있다. 따라서 데이터셋 이름이 같다는 이유만으로 전처리까지 같다고 단정하면 안 된다.

### 3.3 Dataset과 DataLoader의 역할

Dataset은 샘플 하나를 어떻게 읽고 변환할지 정의한다. 초기화 과정에서 파일 경로와 전처리를 준비하고, `__getitem__(idx)`가 호출되면 해당 샘플을 읽어 반환한다.

일반적인 샘플에는 전처리한 이미지 tensor, 정답 mask, 정상·이상 label, 이미지 경로 등이 들어간다. DataLoader는 이런 샘플을 지정된 순서와 배치 크기에 맞춰 묶는다.

```text
파일 경로 목록
    → Dataset.__getitem__(idx): 샘플 하나 읽기·전처리
    → DataLoader: 샘플 여러 개를 배치로 묶기
    → Trainer: 배치를 꺼내 계산에 사용
```

RGB 이미지 8장을 288×288로 묶었다면 이미지 tensor의 shape는 `[8, 3, 288, 288]`이다. 첫 값은 이미지 수, 두 번째는 채널 수, 뒤의 두 값은 높이와 너비다. shape는 크기 정보이고 실제 tensor에는 각 위치의 수치가 들어 있다.

확인한 공통 loader 구성에서 학습 배치 크기는 `args.batch_size`, 검증·테스트 배치 크기는 1이다. 검증 데이터가 없으면 `validation_loader`는 `None`으로 둔다. 학습용 마지막 작은 배치는 `drop_last` 조건에 따라 제외될 수 있다.

DataLoader 생성만으로 이미지가 GPU로 옮겨지지는 않는다. `pin_memory=True`도 GPU 이동 명령이 아니다.

> 흐름 요약: 범주와 Dataset 구현 선택 → split별 Dataset 생성 → 배치를 꺼낼 DataLoader 묶음 반환.

## 4. net: backbone과 method의 Trainer 조립

### 4.1 서로 다른 네 가지 개념

| 이름 | 이 코드에서의 역할 |
|---|---|
| method | PatchCore, SimpleNet처럼 사용할 이상 탐지 방법 |
| backbone | 이미지에서 특징을 추출하는 신경망 |
| `net(args)` | backbone과 설정을 준비해 method의 Trainer를 구성할 함수를 반환하는 함수 |
| Trainer | 해당 method의 준비·학습·추론·평가를 수행하는 객체 |

backbone은 이상 탐지 방법의 구성 요소다. backbone이 특징을 만들고, method는 그 특징을 어떻게 사용해 이상을 판단할지 정한다. 같은 backbone을 사용해도 특징을 저장하는 방식이나 이상 점수 계산이 다르면 다른 method다.

`net`은 여기서 특정 신경망의 이름이 아니다. 모델과 Trainer를 연결하는 준비 코드다.

### 4.2 net(args)의 반환값

`main_net.py`의 `net(args)`는 backbone 이름, 사용할 layer, method의 등록 정보를 준비하고 다음을 반환한다.

```python
("get_simplenet", get_simplenet)
```

`get_simplenet`은 기존 이름이 남아 있는 것이다. 실제 method는 `args.mainmodel`로 선택한다.

runner가 `get_simplenet(input_shape, device)`를 호출하면 backbone과 Trainer를 만들고, `trainer.load(...)`에 설정을 전달한 다음, 준비된 Trainer들의 리스트를 반환한다.

### 4.3 backbone을 가져오는 과정

일반적인 backbone 로딩 경로에서는 이름에 대응하는 생성 함수를 찾아 호출한다. 예를 들어 WideResNet-50 계열의 사전학습 모델을 불러오면 이미 학습된 가중치를 가진 신경망 객체를 얻게 된다.

이것은 현재 검사할 제품의 정상 이미지를 학습했다는 뜻이 아니다. 그 제품을 어떻게 모델에 반영할지는 이후 선택한 method의 실행 과정에 달려 있다.

일부 method는 공통 backbone 로더 대신 내부에서 필요한 모델을 준비한다. 따라서 공통 코드의 `uses_backbone=False`만 보고 그 방법이 특징 추출기를 사용하지 않는다고 해석하면 안 된다. backbone의 동결 여부도 method 구현과 설정을 함께 확인해야 한다.

### 4.4 클래스·객체·실행의 구분

```text
Trainer 클래스 선택: 사용할 설계도를 찾음
Trainer 객체 생성: 설계도로 이번 실행의 객체를 만듦
trainer.load(...): backbone과 실행 설정 등 필요한 구성 요소를 준비함
trainer.train(...): 실제 method의 실행 절차를 시작함
```

`load()`라는 이름이 있다고 항상 checkpoint를 읽는 것은 아니다. 여기서는 모델 구성을 준비하는 역할도 한다.

> 흐름 요약: method 등록 정보 확인 → backbone과 Trainer 객체 생성 → load()로 구성 → Trainer 리스트 반환.

## 5. runner와 Trainer: 학습·추론 실행

### 5.1 runner는 실행 순서를 관리한다

`main_run.py`의 `run()`은 준비된 함수들을 이름으로 찾아 호출한다. DataLoader를 준비하고, 실행 장치를 정한 뒤, seed와 범주를 순회하며 Trainer를 만든다.

이 코드에서는 `get_dataloaders(0)`을 seed 반복문보다 먼저 호출한다. 따라서 데이터 분할에 전달하는 seed 0과 `seed_list`를 돌며 적용하는 실행 seed는 구분해야 한다.

runner는 어떤 범주와 seed에서 나온 결과인지 기록하고 결과를 모은다. 모델 내부에서 특징과 이상 점수를 계산하는 상세 방식은 선택한 Trainer에 맡긴다.

### 5.2 train()이 실행하는 내용은 method에 따라 다르다

공통 실행 경로는 `run_trainer_lifecycle()`을 통해 Trainer의 `train(...)`을 호출하고, 이후 `get_evaluation_metrics()`로 지표를 받는다.

여기서 `train()`이라는 이름만으로 모든 method가 같은 방식으로 가중치를 학습한다고 볼 수 없다. method에 따라 가중치를 갱신하거나, 정상 특징을 모아 메모리를 구성하거나, 필요한 준비와 평가를 수행할 수 있다. 실제 추론과 평가가 어느 시점에 호출되는지는 해당 Trainer 구현에서 결정된다.

### 5.3 배치가 실제 계산에 들어가는 순간

다음은 역할을 구분하기 위한 예시다. 모든 Trainer가 동일한 변수명과 반환 형식을 사용한다는 뜻은 아니다.

```python
images = batch["image"].to(device)
```

이 줄은 배치에서 이미지 tensor를 꺼내 지정한 장치로 옮긴다. 모델 계산을 실행하는 줄은 아니다. 실제 추론은 이후 모델 또는 Trainer의 예측 함수를 호출할 때 일어난다.

`device`는 계산에 사용할 장치를 나타낸다. `cpu`는 CPU, `cuda:0`은 첫 번째 CUDA GPU를 뜻한다. 장치를 지정한 객체를 만들었다고 모든 데이터가 자동으로 같은 장치로 옮겨지는 것은 아니다.

추론 결과에서 구분할 것은 두 가지다.

- 이미지 이상 점수: 이미지 전체가 얼마나 이상한지 나타내는 값.
- anomaly map: 이미지의 위치별 이상 점수를 담은 배열.

이미지 점수를 map의 최댓값으로 만드는 방법도 있지만, 모든 method가 반드시 그렇게 계산하는 것은 아니다.

> 흐름 요약: runner가 범주·seed별 실행 관리 → Trainer가 method 계산 수행 → 예측 및 평가 결과 수집.

## 6. anomaly map 후처리

### 6.1 후처리가 필요한 이유

모델이 계산한 patch 점수 격자는 평가할 이미지나 mask보다 작을 수 있다. 이 경우 점수 격자를 목표 크기로 확대하고, 필요한 경우 부드럽게 만들거나 점수 스케일을 정리한다.

`common.py`의 `RescaleSegmentor`에는 bilinear 보간과 Gaussian smoothing이 구현되어 있다. 확인한 구현은 가로 크기가 다른 조건에서 확대와 smoothing을 수행하고, 그 조건을 통과하지 않으면 기존 map을 반환한다. 모든 method가 이 클래스를 거친다고 일반화해서는 안 된다.

일부 평가 경로는 `normalize_segmentations()`도 호출한다. 정규화가 있다는 이유만으로 출력이 항상 확률이거나 모든 값이 0~1이라고 단정할 수는 없다. 실제 수식과 적용 범위를 확인해야 한다.

### 6.2 anomaly map과 정답 mask는 다르게 다룬다

| 구분 | anomaly map | 정답 mask |
|---|---|---|
| 출처 | 모델의 예측 | 데이터셋의 annotation |
| 값의 의미 | 위치별 연속적인 이상 점수 | 정상·결함 위치의 정답 label |
| 크기 변환 시 고려 | 점수 사이를 보간할 수 있음 | 원래 label을 유지해야 함 |

정답 mask에 bilinear 보간을 적용한 뒤 0이 아닌 값을 모두 결함으로 처리하면 경계의 작은 중간값까지 결함이 될 수 있다. 공통 mask 처리에서 nearest 보간을 사용하는 이유는 이 label 혼합을 피하기 위해서다.

이 수정은 모델의 예측을 직접 바꾸는 것이 아니라 평가에 쓰는 정답 처리를 바꾸는 것이다. 반면 anomaly map의 보간이나 smoothing을 바꾸면 예측 점수 자체가 달라질 수 있다.

크기뿐 아니라 위치도 맞아야 한다. 이미지와 mask가 모두 288×288이어도 resize 비율이나 crop 위치가 다르면 같은 좌표가 같은 원본 위치를 뜻하지 않을 수 있다.

> 흐름 요약: method의 점수 맵을 평가 크기로 준비 → 이미지·정답 mask와 좌표 대응 확인 → 평가 함수에 전달.

## 7. metric: 예측과 정답의 비교

### 7.1 Image AUROC와 Pixel AUROC

| 지표 | 예측 입력 | 정답 입력 | 확인하는 것 |
|---|---|---|---|
| Image AUROC | 이미지별 이상 점수 | 이미지별 정상·이상 label | 이상 이미지에 더 높은 점수를 주는가 |
| Pixel AUROC | 위치별 anomaly map 점수 | 위치별 정답 mask | 결함 위치에 더 높은 점수를 주는가 |

`metrics_gpu.py`의 `compute_imagewise_retrieval_metrics()`는 이미지 점수와 label을 받고, `compute_pixelwise_retrieval_metrics()`는 anomaly map과 mask를 받는다.

픽셀 평가는 예측과 정답을 같은 순서로 1차원으로 펼쳐 각 위치의 점수와 label을 짝지어 계산한다. 펼치는 것은 값을 없애거나 평균내는 일이 아니다. 위치별 비교를 할 수 있도록 배열 형태를 바꾸는 것이다.

### 7.2 AUROC와 판정 기준값은 다르다

AUROC는 여러 기준값에서 정상과 이상을 얼마나 잘 구분하는지 요약하는 지표다. “0.5 이상이면 결함” 같은 하나의 판정 기준값 자체가 아니다.

예를 들어 정상 위치의 점수가 기준값보다 높아 결함으로 판정되면 오탐이다. 기준값을 높이면 같은 점수 배열에서 결함으로 판정되는 위치는 줄거나 그대로 유지된다. 이 변화와 AUROC 값은 구분해서 설명해야 한다.

### 7.3 공통 평가에서도 확인할 점

runner의 `args.pixel_auroc`는 mask 유무에 따라 픽셀 평가 여부를 정하는 용도로 사용된다. 이 설정값 자체가 계산된 Pixel AUROC는 아니다.

계산하지 않은 지표에 `-1`이 들어가는 경로도 있다. 따라서 결과 표에서 `-1`을 실제 성능이나 -100%로 해석하면 안 된다. PRO 계산 함수가 파일에 있다는 사실만으로 이번 실행에서 PRO를 계산했다고 볼 수도 없다.

> 흐름 요약: 이미지 점수·label 비교 / 위치 점수·mask 비교 → 지표 딕셔너리 반환 → 실행 정보와 함께 수집.

## 8. 결과 저장과 W&B의 역할

### 8.1 결과 표와 CSV

runner는 범주 이름, seed, 평가 지표를 하나의 결과 항목으로 모은다. 이 항목들을 DataFrame으로 정리해 출력하고 `args.results_path` 아래의 실행별 경로에 CSV로 저장한다.

CSV는 계산된 결과를 다시 확인하기 위한 기록이다. 모델 가중치나 학습 재개 상태를 저장하는 checkpoint와는 다르다.

### 8.2 W&B는 실험 기록 도구다

W&B는 실행 설정과 지표를 연결해 기록하고 여러 실험을 비교하는 데 사용한다. 모델 대신 학습하거나 AUROC를 계산하는 구성 요소는 아니다.

`main()`은 `args.wan`이 참일 때 다음을 실행한다.

```python
wandb.init(project=args.log_project, config=vars(args))
```

`vars(args)`는 args의 속성들을 딕셔너리 형태로 가져온다. 이 값을 기록하면 어떤 설정으로 얻은 결과인지 함께 확인할 수 있다. `args.log_project`는 기록을 묶을 W&B 프로젝트 이름이다.

이 코드의 CLI 옵션은 `--enable-wandb`이며 내부 설정 이름은 `wan`이다. runner는 W&B 사용 시 실행 결과와 평균 지표 등을 추가로 기록한다.

W&B를 끄는 것은 이 기록 경로를 사용하지 않는다는 뜻이다. 그것만으로 프레임워크 실행이나 CSV 저장이 꺼지지는 않는다. 또한 `wandb.init()`과 지표 기록만으로 데이터셋·모델·checkpoint가 모두 자동 보관되는 것은 아니다.

### 8.3 세 가지 기록을 구분한다

- 로그: 지금 어떤 단계가 실행되는지 확인하는 메시지.
- CSV: 실행 후 비교할 평가 결과 표.
- W&B: 실행 설정과 지표를 묶어 관리하는 실험 기록.

> 흐름 요약: 평가 결과를 실행 정보와 결합 → CSV 저장 → W&B 사용 시 설정·지표도 기록.
