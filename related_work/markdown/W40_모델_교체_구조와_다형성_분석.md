# W40 모델 교체 구조와 다형성 분석

## 한 줄 결론

이 저장소는 설정의 `method` 값만 바꾸면 PatchCore, SimpleNet 등 서로 다른 이상 탐지 방법을 같은 실행 흐름에서 바꿔 실행한다. 실행 담당 코드가 각 알고리즘의 내부를 직접 알 필요 없도록, registry와 공통 Trainer API를 사용한다.

## 1. 무엇이 ‘교체’되는가

```yaml
method: simple
# method: patchcore
```

위 한 줄은 “SimpleNet으로 실행하라”는 선택표다. 이 값이 바뀌면 실제로 생성되는 Python class가 바뀐다.

| method 값 | 실제 class | 핵심 점수 원리 |
|---|---|---|
| `simple` | `Trainer_SimpleNet` | 판별기(discriminator)가 patch feature를 이상으로 보는 정도 |
| `patchcore` | `Trainer_PatchCore` | 정상 memory bank에서 가장 가까운 feature까지의 거리 |
| `rd` | `Trainer_RD` | encoder와 decoder feature의 복원 차이 |
| `dinomaly` | `Trainer_Dinomaly` | encoder/decoder token feature의 차이 |
| `uniad` | `Trainer_UniAD` | 재구성 prediction map |

따라서 11개 방법은 하나의 모델 안에 동시에 들어 있는 것이 아니라, 같은 framework가 선택할 수 있는 서로 다른 이상 탐지 구현이다.

## 2. 전체 연결 흐름

```text
experiment.yaml 또는 명령행 옵션
       │  method="simple" / "patchcore"
       ▼
main.py::resolve_args()
       │  실행 설정 args를 완성
       ▼
component_registry.py::METHOD_REGISTRY
       │  method 이름 → module 경로 + class 이름
       ▼
main_net.py::net()
       │  선택된 Trainer 객체 생성, backbone과 설정 주입
       ▼
main_run.py::run()
       │  train() → get_evaluation_metrics()
       ▼
CSV 결과
```

## 3. registry가 class를 고르는 과정

### 입력

`get_method_spec("patchcore")`의 입력은 문자열 `"patchcore"`다.

### 처리

`component_registry.py`의 `METHOD_REGISTRY`에서 다음 정보를 찾는다.

```text
"patchcore"
  → module: "trainer.trainer_patchcore"
  → class_name: "Trainer_PatchCore"
```

그 다음 `MethodSpec.load_class()`가 다음 순서로 동작한다.

1. `importlib.import_module(module)`로 필요한 trainer 파일만 읽는다.
2. `getattr(module, class_name)`으로 class를 꺼낸다.
3. class가 공통 API를 제공하는지 검사한다.

### 출력

`Trainer_PatchCore`라는 class 자체가 반환된다. 아직 학습된 모델은 아니다. 이후 `MethodSpec.create(device, context)`가 이 class의 객체(instance)를 만든다.

이처럼 필요한 방법을 선택한 뒤에만 import하는 방식을 **lazy import**라고 한다. PatchCore를 사용할 때 PromptAD의 CLIP 라이브러리까지 함께 불러오는 일을 피한다.

## 4. 중요한 코드의 입력·처리·출력

| 코드 | 입력 | 처리 | 출력 |
|---|---|---|---|
| `main.py::resolve_args()` | 기본 YAML, method YAML, CLI 옵션 | 설정 우선순위를 합치고 `args.mainmodel`을 정함 | 실행 설정 `args` |
| `get_method_spec(name)` | `"simple"` 등 method 문자열 | registry에서 해당 `MethodSpec` 조회 | class 위치 정보 |
| `MethodSpec.load_class()` | module/class 이름 | 동적 import, public API 검사 | Trainer class |
| `main_net.net(args)` | args, backbone 이름, 추출 layer | method별 trainer 생성 함수를 준비 | `get_simplenet` hook |
| `get_simplenet(input_shape, device)` | 예: `(3,288,288)`, GPU device | backbone load → trainer 생성 → `load(...)`로 공통 설정 전달 | 준비된 trainer list |
| `run_trainer_lifecycle(...)` | trainer, train/val/test loader, dataset 이름 | `trainer.train(...)` 뒤 metric 요청 | metric dictionary |

`get_simplenet`은 이름 때문에 SimpleNet 전용처럼 보이지만, 과거 호환성을 위해 남은 이름이다. 내부에서는 현재 선택된 `method_spec.create(...)`를 호출하므로 PatchCore를 고르면 PatchCore 객체가 만들어진다.

## 5. 다형성이란 무엇인가

다형성은 runner가 구체적인 모델 종류를 몰라도 같은 이름의 동작을 요청할 수 있는 구조다.

```python
# main_run.py가 기대하는 동작을 단순화한 예시
trainer.train(training_data, validation_data, test_data, dataset_name)
metrics = trainer.get_evaluation_metrics()
```

위 코드에서 `trainer`는 SimpleNet일 수도 PatchCore일 수도 있다. runner는 내부가 판별기인지, memory bank인지 구별하지 않는다. 두 객체가 같은 약속을 지키기 때문이다.

이 저장소의 Trainer contract는 아래 다섯 함수다.

```text
load()
train()
predict()
get_evaluation_metrics()
set_model_dir()
```

`component_registry.py::validate_trainer_class()`는 registry에서 꺼낸 class에 이 함수들이 실제로 있는지 확인한다. 없다면 실행 전에 `ComponentContractError`를 낸다.

## 6. 상속과 contract의 차이

- **상속**: `Trainer_SimpleNet`, `Trainer_PatchCore`는 공통 부모 `Trainer`를 상속한다. 그래서 feature 추출, patch score를 map으로 되돌리기, 평가 같은 코드를 재사용한다.
- **contract**: runner 입장에서 필요한 함수와 입출력의 약속이다. 꼭 내부 알고리즘이 같다는 뜻은 아니다. COAD처럼 구현 구조가 다르더라도 위 함수를 제공하면 같은 runner에 연결할 수 있다.

쉽게 말해 상속은 “공통 부품을 물려받는 방법”, contract는 “교체해도 콘센트 모양이 같다는 약속”이다.

## 7. SimpleNet과 PatchCore: 같은 입력, 다른 처리

두 방법은 공통적으로 이미지 batch에서 patch feature를 만든다.

```text
image batch [B, 3, H, W]
  → backbone feature
  → patch feature [B×P, D]
  → 방법별 _get_pred_scores(features)
  → patch score
  → anomaly map + image score
```

### SimpleNet

| 단계 | 내용 |
|---|---|
| 입력 | test patch feature `features` |
| 처리 | `Trainer_SimpleNet._get_pred_scores()`가 `-self.discriminator(features)` 계산 |
| 출력 | patch별 anomaly score |

SimpleNet의 `train()`은 정상 feature와 합성 noise feature를 구분하도록 discriminator를 학습한다. 추론 때는 discriminator 출력의 부호를 반대로 바꿔 큰 값이 “더 이상함”을 뜻하게 맞춘다.

### PatchCore

| 단계 | 내용 |
|---|---|
| 입력 | test patch feature `features` |
| 처리 | `Trainer_PatchCore._get_pred_scores()`가 FAISS nearest-neighbour search 수행 |
| 출력 | 정상 memory bank의 가장 가까운 feature까지의 거리 |

PatchCore의 `train()`은 일반적인 분류기 학습보다 정상 train feature를 모아 memory bank로 만드는 준비 단계에 가깝다. test patch가 저장된 정상 feature와 멀수록 이상 score가 높아진다.

## 8. 공통 흐름에서 어디까지 같고 어디부터 다른가

| 단계 | 공통 여부 | 설명 |
|---|---|---|
| Dataset/DataLoader | 공통 | `image`, `mask`, `is_anomaly` key를 가진 batch를 전달 |
| backbone feature 추출 | 대부분 공통 | 부모 `Trainer`의 embedding 흐름을 활용하는 방법이 많음 |
| patch feature | 대부분 공통 | PatchMaker가 위치를 유지한 feature patch 묶음으로 만듦 |
| `_get_pred_scores()` | 방법별 | SimpleNet은 discriminator, PatchCore는 NN distance |
| anomaly map/image score | 공통 base Trainer 계열은 공통 | patch score를 grid로 복원하고 map으로 확대 |
| AUROC/CSV 저장 | 공통 | runner가 method를 몰라도 metric dict와 CSV를 처리 |

## 9. 새 방법을 추가하는 최소 순서

1. 새 Trainer class를 만든다.
2. `load`, `train`, `predict`, `get_evaluation_metrics`, `set_model_dir`을 제공한다.
3. 가능하면 공통 `Trainer`를 상속해 embedding/map/evaluation 코드를 재사용한다.
4. `METHOD_REGISTRY`에 method 이름과 module/class 정보를 등록한다.
5. method별 YAML 설정이 필요하면 `configs/`에 추가한다.
6. `method: 새이름`으로 실행해 contract 검사를 통과하는지 확인한다.

## 10. 읽는 순서

1. `main.py::resolve_args()`: method 문자열이 어디서 결정되는지 확인한다.
2. `component_registry.py::METHOD_REGISTRY`: 문자열이 어느 class를 뜻하는지 확인한다.
3. `main_net.py::net()`: class가 실제 객체가 되고 `load()`를 받는 과정을 본다.
4. `component_registry.py::run_trainer_lifecycle()`: 모든 방법에 공통인 실행 순서를 본다.
5. `trainer/trainer.py`: 공통 부모의 embedding, predict, evaluation 흐름을 본다.
6. `trainer/trainer_simplenet.py`, `trainer/trainer_patchcore.py`: 같은 빈자리를 각 방법이 어떻게 다르게 채우는지 비교한다.

## 11. 파일별로 보면 무엇이 바뀌는가

아래 표는 “PatchCore에서 SimpleNet으로 바꾸고 싶다”는 상황에서 각 파일이 실제로 어떤 역할을 하는지 정리한 것이다.

| 파일 | 실행 중 하는 일 | 기존 방법 교체 시 수정 여부 | 새 방법 추가 시 수정 여부 |
|---|---|---|---|
| `experiment.yaml` 또는 CLI | `method`, dataset, backbone 등 실행 선택값 보관 | **수정함**: `method` 값만 교체 | **수정함**: 새 method 이름 사용 |
| `main.py` | YAML/CLI 설정을 합쳐 `args.mainmodel` 생성 | 수정하지 않음 | 보통 수정하지 않음 |
| `component_registry.py` | method 이름과 Trainer class를 연결, contract 검사 | 수정하지 않음 | **수정함**: `METHOD_REGISTRY`에 한 줄 추가 |
| `main_net.py` | 선택된 class 객체 생성, backbone과 공통 설정을 `load()`에 전달 | 수정하지 않음 | 보통 수정하지 않음 |
| `main_run.py` | DataLoader 반복, `train()`, metric 수집, CSV 저장 | 수정하지 않음 | 보통 수정하지 않음 |
| `trainer/trainer.py` | 공통 부모 class: feature, patch, predict, map, 평가 | 수정하지 않음 | 공통 흐름을 쓸 경우 수정하지 않음 |
| `trainer/trainer_simplenet.py` | SimpleNet 전용 discriminator 처리 | 수정하지 않음 | 새 class 파일로 대체/참조 |
| `trainer/trainer_patchcore.py` | PatchCore 전용 memory bank·FAISS 처리 | 수정하지 않음 | 새 class 파일로 대체/참조 |
| `configs/<method>.yaml` | 방법만의 hyperparameter | 선택 방법의 config가 자동 선택됨 | 필요하면 새로 생성 |

즉, **이미 등록된 두 방법을 바꾸는 경우 실행 코드 파일은 고치지 않는다.** 설정의 `method` 값만 바뀌고, registry가 다른 class를 골라 준다. 코드 자체를 새 알고리즘으로 확장할 때만 Trainer 파일과 registry를 추가로 바꾼다.

## 12. PatchCore ↔ SimpleNet 교체: 실제로 바뀌는 코드

### 12.1 사용자가 바꾸는 한 줄

```yaml
# PatchCore 실행
method: patchcore

# SimpleNet 실행 시에는 이 한 줄만 변경
method: simple
```

또는 명령행에서 `--method patchcore`를 `--method simple`로 바꾼다. `main.py`가 이 값을 `args.mainmodel`에 저장한다.

### 12.2 framework 내부에서 자동으로 바뀌는 한 줄

`component_registry.py`에는 이미 다음과 같은 mapping이 있다.

```python
"simple": MethodSpec("trainer.trainer_simplenet", "Trainer_SimpleNet", "simple")
"patchcore": MethodSpec("trainer.trainer_patchcore", "Trainer_PatchCore", "patchcore")
```

따라서 `args.mainmodel` 값이 `"patchcore"`이면 `Trainer_PatchCore`, `"simple"`이면 `Trainer_SimpleNet`이 선택된다. `main_net.py`의 아래 호출은 두 경우에 동일하다.

```python
method_spec = get_method_spec(args.mainmodel)
trainer = method_spec.create(device, context)
trainer.load(backbone=backbone, ..., args=args)
```

여기서 달라지는 것은 `method_spec.create()`가 생성하는 **객체의 class**다. 호출 문장, 전달하는 backbone, `load()`의 공통 인자는 그대로다.

### 12.3 생성되는 객체와 class 관계

```text
DiscriminatorMixin + VisualizationMixin
                 │
                 ▼
             Trainer  ← 공통 부모 class
              │   │
              │   └───────────────────────────────┐
              ▼                                   ▼
   Trainer_SimpleNet                    Trainer_PatchCore
   - discriminator                      - anomaly_scorer
   - pre_projection (선택)              - featuresampler
   - _get_pred_scores()                 - _meta_train()
                                         - _get_pred_scores()
```

`Trainer`는 `load()`, `train()`, `predict()`, `get_evaluation_metrics()`, `set_model_dir()`의 공통 동작을 제공한다. 자식 class는 자기 방법만 달라야 하는 부분을 덮어쓴다(override).

## 13. class 안에서 어떤 함수가 달라지는가

### 13.1 공통 부모 `Trainer`

| 함수 | 입력 | 처리 | 출력/효과 |
|---|---|---|---|
| `load(backbone, layers, device, input_shape, ...)` | backbone, 추출 layer, GPU/CPU, hyperparameter | feature aggregator·PatchMaker·segmentor를 만들고, 자식의 `initialize_model()` 호출 | 학습/추론 가능한 객체 상태 |
| `train(train, val, test, dataset_name)` | 세 DataLoader와 이름 | 공통 학습 lifecycle을 실행하고 자식 hook으로 내려감 | 학습 완료 및 evaluation 기록 |
| `predict(data)` | test DataLoader | batch별 `_predict(images, mask)` 호출 | image score, anomaly map, feature, label, mask |
| `_predict(images, mask_gt)` | image batch | feature 추출 → 자식의 `_get_pred_scores()` → patch score를 map으로 복원 | image score와 anomaly map |
| `get_evaluation_metrics()` | 기록된 평가 결과 | AUROC 등 metric을 평균/정리 | 문자열 key를 갖는 metric dict |

중요한 점은 부모 `Trainer._predict()`가 **점수를 어떻게 만들지는 모른다**는 것이다. 그 자리에 `self._get_pred_scores(features)`라는 빈 고리(hook)를 둔다. 실행할 때 실제 객체가 SimpleNet이면 SimpleNet 함수가, PatchCore이면 PatchCore 함수가 호출된다.

### 13.2 `Trainer_SimpleNet`이 바꾸는 부분

```python
class Trainer_SimpleNet(Trainer):
    def initialize_model(...):
        # discriminator와 optimizer를 준비

    def _get_pred_scores(self, features):
        return -self.discriminator(features)
```

| 항목 | 내용 |
|---|---|
| 입력 | patch feature tensor `features` |
| 처리 | 학습된 discriminator에 feature를 넣음 |
| 출력 | patch별 score. 부호를 반대로 해 큰 값이 이상을 뜻하게 함 |

SimpleNet은 부모가 만든 patch feature를 판별기에 전달하는 방식으로 교체 지점을 채운다.

### 13.3 `Trainer_PatchCore`가 바꾸는 부분

```python
class Trainer_PatchCore(Trainer):
    def initialize_model(...):
        # nearest-neighbour scorer와 coreset sampler 준비

    def _meta_train(...):
        # normal feature를 모아 memory bank 구성

    def _get_pred_scores(self, features):
        return self.anomaly_scorer.predict([features.cpu().numpy()])[0]
```

| 항목 | 내용 |
|---|---|
| 입력 | patch feature tensor `features` |
| 처리 | tensor를 NumPy로 바꾸고, FAISS가 memory bank에서 최근접 정상 feature를 검색 |
| 출력 | patch별 최근접 거리. 멀수록 이상 score가 큼 |

PatchCore는 분류기 weight를 학습하는 대신 `_meta_train()`에서 정상 feature memory bank를 채운다. 그래서 같은 `train()` 호출이라도 자식 class에 따라 실제 학습 준비가 달라진다.

## 14. 새 모델 class를 추가할 때 코드가 바뀌는 곳

예를 들어 `NewMethod`라는 새 알고리즘을 추가한다고 하자. 아래는 **구조를 설명하기 위한 예시**이며, 현재 저장소의 실행 코드를 변경하라는 뜻은 아니다.

### 14.1 새 Trainer 파일

`trainer/trainer_newmethod.py`에 공통 부모를 상속한 class를 만든다.

```python
from trainer.trainer import Trainer

class Trainer_NewMethod(Trainer):
    def initialize_model(self, **kwargs):
        # NewMethod만의 네트워크, 통계량, optimizer를 준비한다.
        ...

    def _get_pred_scores(self, features):
        # [B×P, D] patch feature를 받아 [B×P] 점수로 바꾼다.
        return new_method_score(features)
```

이 방법이 공통 feature → patch score → map 흐름을 사용할 수 있다면 위 두 hook만으로 충분할 수 있다. 학습 방식이 특별하면 `_meta_train()`도 override한다. 입력/출력 형태를 유지하면 부모 `Trainer`의 `predict()`와 evaluation을 재사용할 수 있다.

### 14.2 registry에 새 이름 등록

`component_registry.py`의 `METHOD_REGISTRY`에 다음 한 항목을 넣는다.

```python
"newmethod": MethodSpec(
    "trainer.trainer_newmethod",
    "Trainer_NewMethod",
    "newmethod",
)
```

이 한 줄이 없으면 `method: newmethod`가 어떤 파일/class를 뜻하는지 framework가 알 수 없다.

### 14.3 config와 실행 선택

```yaml
# configs/newmethod.yaml
method: newmethod
```

그 뒤 `method: newmethod`로 실행하면 흐름은 기존 방법과 같다.

```text
method 문자열
 → Trainer_NewMethod 생성
 → 부모 Trainer.load()
 → NewMethod.initialize_model()
 → 부모 Trainer.train()/predict()
 → NewMethod._get_pred_scores()
 → 공통 map, AUROC, CSV
```

## 15. 교체할 때 확인할 오류

| 증상 | 가장 먼저 볼 코드 | 흔한 원인 |
|---|---|---|
| `Unknown method` | `METHOD_REGISTRY` | method 문자열 오타 또는 미등록 |
| import 오류 | `MethodSpec.module` | module 경로/의존성 문제 |
| `ComponentContractError` | `validate_trainer_class()` | `load`, `train`, `predict` 등 public API 누락 |
| `NotImplementedError` | `Trainer.initialize_model()` | 자식 class가 전용 초기화를 구현하지 않음 |
| map shape 오류 | `_get_pred_scores()`, `PatchMaker` | patch score 수가 feature patch 수와 맞지 않음 |
| PatchCore score 오류 | memory bank build, `NearestNeighbourScorer` | train 단계에서 normal feature bank가 채워지지 않음 |
