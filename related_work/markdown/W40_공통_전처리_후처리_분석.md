# W40 공통 전처리와 후처리 분석 — DINOMALY 공유 코드베이스

> 이 문서는 딥러닝 이상 탐지를 처음 보는 사람을 위해 작성했다. 처음에는 아래의 “한 장의 이미지 여행”과 용어 설명만 읽고, 구현을 확인해야 할 때 뒤의 코드 경로와 Evidence Map을 보면 된다.

## 먼저 알아둘 네 가지 말

### 정상·이상 이미지

이 코드베이스는 **정상 이미지로 먼저 모델을 학습**한 뒤, 처음 보는 이미지가 정상과 얼마나 다른지를 측정한다. 예를 들어 bottle category라면 깨지지 않은 병 사진이 정상(`good`)이고, 병이 깨진 사진이 이상(`defect`)이다.

### 전처리(preprocessing)

원본 사진 파일은 크기도 다르고 픽셀 값도 0~255 정수다. 모델이 같은 형식으로 읽도록 다음을 수행하는 과정을 전처리라고 한다.

1. 사진을 RGB 세 채널로 연다.
2. 정해진 정사각형 크기로 바꾼다.
3. `0~255` 픽셀을 `0~1` tensor로 바꾼다.
4. ImageNet 평균과 표준편차로 정규화한다.

### Anomaly score와 anomaly map의 차이

- **image anomaly score**: 이미지 한 장에 숫자 하나를 붙인다. 숫자가 클수록 “이 이미지가 이상일 가능성이 높다”는 뜻이다. image AUROC가 이 숫자를 사용한다.
- **anomaly map**: 이미지의 각 위치에 숫자를 붙인 열지도다. 밝은 부분이 모델이 이상하다고 본 위치다. pixel AUROC가 이 map을 정답 mask와 비교한다.

둘은 같은 것이 아니다. image score는 map에서 가장 큰 값이나 상위 1% 평균처럼 map/patch score를 요약해 만들 수 있지만, 방법마다 요약 규칙이 다르다.

### Patch와 feature

모델은 원본 이미지의 모든 픽셀을 한 번에 비교하지 않는다. backbone이 만든 중간 feature map을 작은 지역 단위인 **patch**들로 나누고, 각 patch를 숫자 벡터(feature embedding)로 바꾼다. 이후 각 patch가 학습 때 본 정상 patch들과 얼마나 다른지 계산한다.

## 한 장의 이미지 여행: 파일에서 이상 히트맵까지

아래는 기본 MVTec 형식에서 test 이미지 `bottle/test/broken_large/000.png` 한 장이 들어왔을 때의 공통 흐름이다. SimpleNet과 PatchCore는 마지막 “patch 점수 만들기”만 다르고, 앞부분과 map으로 되돌리는 과정은 공통이다.

```text
PNG 파일 + 정답 mask PNG
  │
  ├─ Dataset: 파일 경로와 good/defect 라벨을 읽음
  ├─ Transform: RGB → resize → tensor → ImageNet 정규화
  ├─ DataLoader: image/mask/label을 dict batch로 묶음
  ├─ Backbone: layer2, layer3의 중간 feature map을 꺼냄
  ├─ Patchify: feature map을 겹치는 작은 patch들로 나눔
  ├─ Score: 각 patch가 정상 patch와 얼마나 다른지 계산
  ├─ Image score: patch들 가운데 가장 큰 점수 하나를 선택
  └─ Anomaly map: patch 점수 격자를 mask 크기로 키우고 부드럽게 만듦
      └─ 평가: image score ↔ good/defect, map ↔ 정답 mask
```

예를 들어 어떤 이미지의 patch 점수가 `[0.02, 0.05, 0.81, 0.12]`라면, 기본 공통 경로의 image score는 최대값 `0.81`이다. `0.81`이 있던 patch 위치는 anomaly map에서 밝은 위치가 된다. 이 값 자체가 “81% 확률”이라는 뜻은 아니다. 정상과의 거리 또는 모델 logit처럼 방법 안에서만 의미 있는 상대 점수다.

## 이 코드베이스를 이해하기 위한 단계별 학습 경로

처음부터 144개 Python 파일을 순서대로 읽을 필요는 없다. 그 방법은 OpenCLIP, DINO, optimizer처럼 외부 논문 구현의 세부사항에 먼저 막히기 쉽다. 아래 순서대로 “입력 → 처리 → 출력”의 큰 흐름을 이해한 뒤, 관심 방법의 trainer와 하위 라이브러리로 내려가는 것이 좋다.

### 0단계 — Python과 PyTorch에서 최소로 알아야 할 것

먼저 아래 네 가지 문법/개념만 익히면 이 저장소의 공통 경로를 읽을 수 있다.

| 알아야 할 것 | 이 코드에서 왜 필요한가 | 처음 보는 위치 |
|---|---|---|
| `dict`, `list`, class, 상속 | sample은 dict이고, Dataset/Trainer는 부모 class를 상속한다 | `datasets/base.py`, `trainer/trainer.py` |
| `torch.Tensor`와 shape | 이미지, feature, mask가 모두 tensor이며 shape가 처리 의미를 결정한다 | `datasets/base.py`, `trainer/trainer.py` |
| `Dataset`, `DataLoader` | 파일 목록에서 image를 하나씩 읽고 batch로 묶는다 | `main_dataset.py` |
| `model.train()`, `model.eval()`, `torch.no_grad()` | 학습 시 gradient를 계산하고, 추론 시에는 계산을 끈다 | `trainer/trainer.py` |

여기서 가장 중요한 습관은 tensor 옆의 shape를 읽는 것이다. 예를 들어 `[B, 3, 288, 288]`에서 `B`는 batch 안의 이미지 수, `3`은 RGB channel, 나머지는 높이와 너비다. `[B, 1, 224, 224]` mask의 `1`은 grayscale mask channel이다.

**확인 질문:** `DataLoader`가 image를 직접 만드는가? 아니다. Dataset이 image dict 하나를 만들고, DataLoader는 여러 dict를 batch로 묶는다.

### 1단계 — 이상 탐지 문제를 먼저 이해하기

이 저장소의 목적은 일반적인 “고양이/개 분류”와 다르다. 모델은 defect 종류를 맞히기보다, **정상 학습 이미지와 다른 부분을 찾아야 한다.**

| 용어 | 쉬운 뜻 | 코드에서의 표현 |
|---|---|---|
| normal / good | 학습 때 보여 주는 정상 제품 | `anomaly == "good"`, `is_anomaly == 0` |
| anomaly / defect | 긁힘, 파손 등 정상과 다른 제품 | `anomaly != "good"`, `is_anomaly == 1` |
| image-level detection | 사진 전체가 이상인지 판정 | image anomaly score, image AUROC |
| pixel-level localization | 사진의 어느 위치가 이상인지 찾기 | anomaly map, mask, pixel AUROC |

**확인 질문:** defect mask가 없어도 image AUROC는 계산할 수 있는가? 가능하다. good/defect label만 있으면 된다. 반대로 pixel AUROC에는 각 pixel의 정답 mask가 필요하다.

### 2단계 — 데이터 폴더와 sample 하나를 이해하기

다음으로 `datasets/mvtec.py`와 `datasets/base.py`를 읽는다. 이 단계의 목적은 “모델이 받는 한 장의 데이터는 정확히 무엇인가”를 아는 것이다.

```text
MVTec 폴더의 PNG 한 장
  → BaseDataset.__getitem__(idx)
  → {image, mask, is_anomaly, classname, image_path, ...}
```

이 단계에서 꼭 확인할 코드는 다음 순서다.

1. `datasets/mvtec.py::_get_image_data()` — 폴더에서 image/mask path 목록을 만드는 부분
2. `datasets/base.py::__getitem__()` — path를 열어 tensor dict로 바꾸는 부분
3. `datasets/base.py::transform_img`, `transform_mask` — resize와 정규화 부분

**확인 질문:** `image`와 `mask`의 크기가 항상 같은가? 아니다. 현재 기본 SimpleNet 설정에서는 image는 288×288, mask는 224×224이다.

### 3단계 — 설정값이 어떤 파일을 실행하게 하는지 이해하기

이제 `experiment.yaml`을 열고 `main.py`를 읽는다. 여기서는 딥러닝 수식보다 **선택한 이름이 실제 구현으로 연결되는 과정**을 이해한다.

```text
method: patchcore
dataset: mvtec
category: bottle
        ↓
component_registry.py
        ↓
Trainer_PatchCore + MVTecDataset 선택
```

읽는 순서는 `main.py::resolve_args()` → `component_registry.py::METHOD_REGISTRY` → `component_registry.py::DATASET_REGISTRY`가 좋다. `configs/patchcore.yaml`처럼 method별 YAML은 공통 default를 덮어쓰는 값이다.

**확인 질문:** `method: glass`, `dataset: mvtec`이면 일반 MVTec Dataset을 쓰는가? 아니다. registry가 GLASS 전용 MVTec Dataset으로 자동 치환한다.

### 4단계 — Dataset이 batch가 되는 과정을 이해하기

`main_dataset.py`는 앞 단계의 Dataset class를 train/validation/test 세 개로 만들고 DataLoader로 감싼다. 여기에서 확인할 것은 batch 크기와 shuffle이다.

```text
Dataset: index 하나 → sample dict 하나
DataLoader(training): 여러 sample → batch dict, shuffle=True
DataLoader(testing): 한 sample → batch dict, shuffle=False
```

처음에는 `_make_loader()`와 `get_dataloaders()`만 읽으면 충분하다. `num_workers`, `pin_memory`, `drop_last`는 성능/안정성 옵션이며, 이상 점수의 수식 자체를 바꾸지 않는다.

### 5단계 — Backbone feature와 patch를 이해하기

`trainer/trainer.py::_embed()`과 `common.py`를 읽는다. 이 단계가 가장 중요한 중간 고리다. 원본 image가 바로 anomaly score가 되는 것이 아니라, backbone의 중간 feature를 patch 단위로 바꾸어 비교한다.

```text
image [B,3,H,W]
  → WideResNet/DINO 등의 backbone
  → layer feature map [B,C,Hf,Wf]
  → patchify
  → patch embedding [B·P,D]
```

처음에는 아래만 이해하면 된다.

- **hook**: backbone 전체 출력을 바꾸지 않고, 지정한 중간 layer output을 꺼내는 장치다.
- **feature map**: 이미지의 위치별 의미 정보를 담은 작은 격자다.
- **patchify**: 격자의 한 위치 주변을 묶어 지역 feature 하나를 만드는 과정이다.
- **embedding**: patch를 비교하기 쉽게 길이가 맞춰진 숫자 벡터다.

**확인 질문:** 왜 여러 layer feature를 같은 patch 격자로 맞추는가? 서로 다른 layer의 정보를 같은 이미지 위치끼리 합치기 위해서다.

### 6단계 — score 하나와 anomaly map 하나가 나오는 과정을 이해하기

이제 `trainer/trainer.py::_predict()` → `PatchMaker.score()` → `common.py::RescaleSegmentor` 순서로 읽는다.

1. 방법별 함수가 각 patch의 이상 점수를 계산한다.
2. `PatchMaker.score()`가 가장 높은 patch 점수로 image score를 만든다.
3. patch 점수를 2차원 격자로 되돌린다.
4. 작은 격자를 정답 mask 크기로 확대하고 smoothing하여 anomaly map을 만든다.

이 네 단계는 **SimpleNet과 PatchCore를 읽는 공통 뼈대**다. score의 원천만 다르다.

| trainer | patch score를 만드는 질문 |
|---|---|
| SimpleNet | “discriminator가 이 feature를 얼마나 이상으로 보는가?” |
| PatchCore | “이 patch와 가장 가까운 정상 memory-bank patch의 거리는 얼마인가?” |

### 7단계 — 한 가지 방법을 골라 끝까지 추적하기

공통 경로를 이해한 뒤에는 한 방법만 골라 `initialize/load → train → predict` 순서로 읽는다. 처음에는 다음 순서를 권한다.

1. **SimpleNet**: `trainer/trainer_simplenet.py` — 공통 Trainer를 가장 직관적으로 사용한다.
2. **PatchCore**: `trainer/trainer_patchcore.py` — normal memory bank와 최근접 거리라는 대표적인 one-class 방식이다.
3. **RD / Dinomaly / UniAD**: reconstruction mismatch로 map을 만드는 계열이다.
4. **WinCLIP / PromptAD / COAD**: CLIP text prompt 또는 foundation model을 함께 쓰는 계열이다.

한 방법을 읽을 때 “학습 때 무엇을 저장/학습하는가?”, “test patch의 score는 어느 줄에서 만들어지는가?”, “image score를 max·mean·top-k 중 무엇으로 요약하는가?” 세 질문에 답할 수 있으면 충분하다.

### 8단계 — 마지막에 평가와 결과 파일을 읽기

마지막으로 `trainer/trainer.py::_evaluate()`, `metrics_gpu.py`, `main_run.py`를 읽는다. 이 단계는 모델 내부보다 “결과 숫자가 무엇을 뜻하는지”를 확인하는 단계다.

- `image AUROC`: 정상 이미지보다 이상 이미지에 더 높은 score를 주는 순서가 좋은가?
- `pixel AUROC`: 정상 pixel보다 defect pixel에 더 높은 map 값을 주는가?
- CSV: category와 seed별 metric을 한 표로 저장한 결과다.

### 처음 1회에 읽지 않아도 되는 파일

아래는 특정 method를 실제로 깊게 파고들 때 읽으면 된다. 초반에 모두 읽으면 공통 구조를 놓치기 쉽다.

- `trainer/CLIPAD/`, `trainer/WinCLIP_lib/open_clip/`: CLIP 모델 내부, tokenizer, pretrained weight loader
- `trainer/Dinomaly_lib/dinov1/`, `dinov2/`, `beit/`: DINO/BEiT Transformer 세부 구현
- `trainer/*_lib/optimizers/`: Adam 변형 optimizer 수식
- `COAD/backbones/`: COAD용 DINO backbone 세부 구현

## 범위와 결론

이 문서는 하나의 방법 논문을 설명하는 문서가 아니라, 11개 방법을 한 실행 경로에 얹은 이 코드베이스에서 **데이터가 어떤 계약(contract)으로 들어오고**, **공통 경로가 feature·anomaly score·anomaly map을 어떻게 만드는지**, 그리고 **그 공통 경로를 벗어나는 방법은 무엇을 다르게 하는지**를 코드 기준으로 정리한다.

핵심 결론은 다음과 같다.

1. 기본 데이터 계약은 `dict` 배치이며, 최소 핵심 키는 `image`, `mask`, `is_anomaly`이다. 이미지와 mask는 각각 ImageNet 정규화된 RGB tensor와 0/1 이진 mask tensor다.
2. 일반적인 SimpleNet/PatchCore 계열은 `backbone feature → patchify → layer/dimension pooling → patch score → image score + upsampled map`이라는 공통 후처리 경로를 사용한다. 쉽게 말해 “정상에서 벗어난 정도를 지역별로 재고, 그중 가장 수상한 지역으로 이미지 전체를 판정”한다.
3. `rd`, `dinomaly`, `uniad`, `promptad`, `winclip`, `glass`, `coad`는 `predict()` 또는 feature 경로를 재정의한다. 따라서 “공통 score 계산식”을 모든 방법에 동일하게 적용하면 안 된다.
4. 현재 기본 `simple` 설정에서는 실제 모델 입력이 `288×288`, 비교 대상 mask는 `224×224`이다. 설정명 `imagesize`가 항상 transform의 최종 이미지 크기를 뜻하지는 않는다.

## 1. 실행·구성 흐름

```text
experiment.yaml / CLI
  → main.resolve_args(): defaults + configs/<method>.yaml + experiment + CLI merge
  → main_dataset.dataset(args): Dataset/DataLoader 3종 생성
  → main_net.net(args): backbone + registered Trainer 생성 및 load()
  → main_run.run(): train → predict → metric → CSV
```

관련 코드:

- 인자 병합과 기본값: `main.py:40-221`
- method/dataset lazy registry: `component_registry.py:31-166`
- dataset/dataloader 구성: `main_dataset.py:33-252`
- 공통 실행 loop: `main_run.py:33-135`

`experiment.yaml`의 `method`, `dataset`, `category`, `data_path`는 각각 내부적으로 `mainmodel`, `dataset`, `subdatasets`, `data_path`로 정규화된다. category 문자열 안의 `+`는 한 DataLoader에서 여러 클래스를 합치는 표기다. category 목록의 각 원소는 별도 dataloader가 된다.

## 1.1 파일들은 어떻게 연결되는가

이 저장소는 모든 파일이 서로 직접 연결된 구조가 아니다. `main.py`가 입구이고, **registry가 선택할 파일을 결정**하며, 선택된 trainer만 늦게(import lazy) 불러온다. 예를 들어 `method: patchcore`를 골랐을 때만 `trainer/trainer_patchcore.py`가 실제로 import된다. 다른 방법의 무거운 라이브러리를 시작부터 모두 불러오지 않기 위한 구조다.

```text
                         experiment.yaml
                               │ 설정값
                               ▼
                            main.py
              ┌───────────────┼────────────────┐
              │               │                │
              ▼               ▼                ▼
 component_registry.py   main_dataset.py     main_net.py
  "어떤 파일을 쓸까?"   "사진을 어떻게 묶나?"  "어떤 모델을 만드나?"
              │               │                │
       method/dataset spec     │                │ selected Trainer + backbone
              │               ▼                ▼
              │        datasets/*.py    trainer/trainer_*.py
              │               │                │
              │               ▼                ▼
              │          DataLoader       train() / predict()
              └────────────────┬───────────────┘
                               ▼
                           main_run.py
                    반복 실행 · 평가 · CSV 저장
```

### 입구와 조정 파일

| 파일 | 하는 일 | 다음으로 연결되는 파일 |
|---|---|---|
| `experiment.yaml` | 사람이 가장 자주 바꾸는 실험 선택값 | `main.py` |

| `component_registry.py` | method 이름을 trainer 파일/클래스로, dataset key를 Dataset 클래스로 연결 | `main_dataset.py`, `main_net.py` |

### Dataset 파일끼리의 연결

```text
main_dataset.py
  └─ registry에서 고른 Dataset class 생성
```

`datasets/base.py`는 이미지 열기, resize, 정규화, mask 처리, 그리고 반환 dict 형식을 담당하는 부모 클래스다. `mvtec.py`, `lgdata.py`, `explicit_realiad.py`는 각 데이터셋에서 **어떤 파일들이 있는지 목록을 만드는 일**만 주로 다르게 한다. 그래서 새 dataset을 추가할 때는 대개 BaseDataset의 반환 키를 유지하고 `_get_image_data()`만 새 파일 구조에 맞게 구현해야 runner와 호환된다.

### Trainer 파일끼리의 연결

```text
trainer/trainer.py  (공통 Trainer 부모)
```

모든 trainer는 registry가 요구하는 `load()`, `train()`, `predict()`, `get_evaluation_metrics()`, `set_model_dir()`라는 공통 약속을 지킨다. 그래서 `main_run.py`는 방법의 내부 수식을 몰라도 `trainer.train(...)` 다음 `trainer.get_evaluation_metrics()`를 호출할 수 있다. 다만 이 약속은 **입력과 최종 metric을 맞추는 인터페이스**일 뿐, 내부 feature와 score 계산까지 같다는 뜻은 아니다.

## 2. Dataset 선택과 파일을 읽는 방식

### 2.1 Registry와 dataset별 source

| dataset key | 실제 Dataset class | source 형식 | 비고 |
|---|---|---|---|
| `mvtec`, `multi`, `medical`, `visa`, `custom` | `datasets.mvtec.MVTecDataset` | MVTec 디렉터리 | 실제 class name만 달라질 수 있는 공통 layout |
| `lg` | `datasets.lgdata.LGDataset` | JSON mapping → `train/`, `val/`, `test/` 숫자 class 폴더 | `OK`는 good, `NG`는 defect |
| `realiad` | `datasets.explicit_realiad.ExplicitDataset` | Real-IAD metadata JSON + 이미지 root | JSON의 image/mask 상대경로 사용 |
| `mvtec_glass`, `multi_glass` | `trainer.GLASS_lib.mvtec.MVTecDataset` | MVTec layout | `glass`를 고를 때 registry가 자동 치환 |

`component_registry.py:115-143`이 이 mapping을 가진다. `get_dataset_spec()`은 `(mvtec, glass)`와 `(multi, glass)`를 GLASS 전용 dataset으로 바꾼다. 즉, 같은 `mvtec` 선택이라도 method가 `glass`인지에 따라 transform 구현이 바뀐다.

### 2.2 MVTec 계열 파일 열거

`datasets/mvtec.py:21-89`는 선택한 category마다 다음을 찾는다.

```text
<data_path>/<category>/train/<anomaly_type>/*        # TRAIN
<data_path>/<category>/test/<anomaly_type>/*         # TEST 및 VAL
<data_path>/<category>/ground_truth/<defect>/*       # TEST defect mask
```

- 파일명은 정렬(`sorted`)되어 image와 mask를 같은 인덱스로 짝짓는다.
- `good`은 mask path가 `None`이고, defect는 `ground_truth/<defect>/`가 존재할 때만 mask path를 갖는다.
- `is_anomaly = int(anomaly != "good")`이다.
- `subtest`면 각 anomaly type의 앞 1%만 사용한다. `subtrain`이면 train 전체에서 무작위 5%를 다시 고른다.

즉 MVTec dataset은 별도의 CSV annotation을 읽지 않는다. **폴더 이름 자체가 label**이다. `train/good`의 모든 파일은 정상 학습 이미지, `test/good`은 정상 test 이미지, `test/broken_large`는 이상 test 이미지가 된다. defect image의 위치 정답은 같은 defect 이름 아래의 `ground_truth` mask 파일에서 읽는다.

주의할 동작: MVTec 구현은 `TRAIN` 이외 split에서 모두 `test/`를 연다. 또한 mask는 `split == DatasetSplit.TEST`일 때만 읽는다. 그러므로 runner가 만드는 `VAL` dataset은 test image를 기반으로 하지만 mask는 0 tensor이며, `subtest=True`로 잘린다. 이 validation loader는 존재할 수 있으나 공통 base trainer는 기본적으로 이를 점수 평가에 쓰지 않는다.

### 2.3 LG와 Real-IAD

- LG: `datasets/lgdata.py:24-65`가 `data_path`에 지정된 JSON의 `dataset_list`와 `class_categories`를 읽는다. train에는 `OK`만, test/val에는 `OK`와 `NG`를 읽으며 ground-truth pixel mask는 제공하지 않는다.
- Real-IAD: `datasets/explicit_realiad.py:75-190`가 class metadata JSON의 `train` 또는 `test` records를 읽는다. `mask_path is None` 또는 `anomaly_class == normal_class`이면 good으로 분류한다. `zipper`, `toothbrush`만 실제 폴더명에 `_realiad` suffix를 붙인다. 손상된/없는 image 또는 mask 파일은 경고를 남기고 skip한다.

## 3. 공통 전처리: PIL 파일에서 model input까지

### 3.1 BaseDataset transform

`datasets/base.py:68-174`의 현재 활성 transform은 다음뿐이다.

```python
image = Compose([
    Crop(*args.crop) if args.crop is not None else identity,
    Resize((resize, resize)),
    ToTensor(),
    Normalize(IMAGENET_MEAN, IMAGENET_STD),
])

mask = Compose([
    Resize((args.masksize, args.masksize)),
    ToTensor(),
])
```

`PIL.Image.open(...).convert("RGB")`로 image를 열고, test defect mask는 grayscale `L`로 변환한 뒤 resize한다. mask의 0이 아닌 모든 값은 1.0으로 이진화한다. image 정규화 상수는 `mean=[0.485, 0.456, 0.406]`, `std=[0.229, 0.224, 0.225]`다.

코드가 인자로 전달받는 `ColorJitter`, flip, grayscale, affine/rotate, center crop은 현재 BaseDataset transform에서 주석 처리되어 있다. 따라서 `brightness`, `hflip`, `rotate_degrees` 등을 바꾸어도 기본 MVTec dataset에는 적용되지 않는다. 반면 GLASS 전용 dataset (`trainer/GLASS_lib/mvtec.py`)은 해당 augmentation과 center crop을 활성화한다.

정규화는 “사진을 예쁘게 만드는 과정”이 아니라 pretrained backbone이 학습 때 기대했던 숫자 범위에 맞추는 과정이다. 예를 들어 원래 빨강 채널 값이 255인 픽셀은 tensor에서 1.0이 된 후 `(1.0 - 0.485) / 0.229`로 바뀐다. 따라서 model input tensor를 그대로 PNG로 저장하면 원래 색과 다르게 보이며, 시각화하려면 평균·표준편차를 다시 적용해 역정규화해야 한다.

### 3.2 실제 batch 입출력 계약

MVTec `BaseDataset.__getitem__()`의 반환값은 아래와 같다 (`datasets/base.py:120-174`). DataLoader의 default collate가 tensor에는 batch 차원을 붙이고 문자열은 길이 B의 list/tuple로 묶는다.

| key | sample 값 | `batch_size=B`일 때의 형식/shape | 용도 |
|---|---|---|---|
| `image` | 정규화 RGB image | `float32 [B, 3, resize, resize]` | model 입력 |
| `mask` | 0/1 mask | `float32 [B, 1, masksize, masksize]` | pixel 평가/시각화 |
| `is_anomaly` | good=0, defect=1 | integer tensor `[B]` | image AUROC label |
| `classname`, `anomaly` | category, defect type | string collection | method prompt/로그 |
| `image_path`, `image_name`, `text` | 원본 경로, 표시명, 파일명 뒤 3자리 | string collection | 저장/COAD text 등 |
| `fg` | foreground mask 또는 all-one mask | `[B, 1, masksize, masksize]` | 일부 방법의 foreground 처리 |

현재 기본 실행 설정은 `method: simple`, `configs/simple.yaml`의 `resize: 288`, `imagesize: 288`, 그리고 공통 default `masksize: 224`이다. 따라서 crop이 없을 때 한 실제 sample은 다음과 같다.

```text
input  image: [3, 288, 288], ImageNet-normalized float32
target mask : [1, 224, 224], 0.0/1.0 float32
label       : 0 (good) 또는 1 (defect)
```

이 예시는 코드의 기본 config에서 도출한 실제 계약이며, 포함된 dataset/weight가 없으므로 이 문서 작성 시 학습 실행 결과는 아니다. `BaseDataset.imagesize`에는 `(3, imagesize, imagesize)`가 저장되지만, 활성 image transform은 `imagesize` crop을 하지 않고 `resize`만 사용한다. 두 값이 다르면 `imagesize` metadata와 실 tensor shape가 달라질 수 있다.

## 4. DataLoader 구성

`main_dataset.py:69-252`는 train/validation/test dataset을 모두 만들고 다음처럼 loader를 구성한다.

| split | batch size | shuffle | 기타 |
|---|---:|---|---|
| training | `args.batch_size` (method config별) | True | 마지막 batch의 잔여가 1개면 `drop_last=True` 가능 |
| validation | 1 | False | dataset이 비어 있으면 `None` |
| testing | 1 | False | 항상 생성 |

공통 옵션은 `num_workers=args.num_workers`(기본 1), `pin_memory=True`, worker가 1 이상이면 `prefetch_factor=2`다. seed는 `get_dataloaders(0)`으로 dataset 구성 시 0을 넣고, `main_run.py`는 각 model seed마다 `utils.fix_seeds()`를 호출한다. 즉 코드 주석대로 dataset 구성 자체는 seed loop 밖에 있어, 기본 흐름에서 seed는 주로 model/학습의 난수성에 작용한다.

초보자 관점에서 Dataset과 DataLoader를 구분하면 쉽다. Dataset은 “index 17을 주면 17번째 사진과 label dict를 돌려주는 목록”이고, DataLoader는 그 목록에서 여러 개를 꺼내 batch로 묶고 순서를 섞는 도구다. 이 코드에서는 test batch를 항상 1장으로 둔다. 그래서 대부분의 자체 `predict()` 구현은 `[1, 3, H, W]` 입력을 전제로 map 한 장과 score 하나를 만든다.

## 5. 공통 feature 전처리와 patch 표현

이 절은 `Trainer` base class를 상속하고 base `predict()`를 쓰는 경로의 핵심이다.

### 5.1 Backbone activation을 가져오는 방법

`common.NetworkFeatureAggregator` (`common.py:176-265`)은 지정 layer에 forward hook을 등록한다. 기본 SimpleNet/PatchCore는 `wideresnet50`의 `layer2`, `layer3` activation을 꺼낸다.

```text
normalized image [B,3,H,W]
  → backbone
  → hook outputs {layer2: [B,C2,H2,W2], layer3: [B,C3,H3,W3]}
```

Transformer feature가 `[B,L,C]`이면 `Trainer._embed()`이 `L`이 완전제곱수라고 가정하여 `[B,C,sqrt(L),sqrt(L)]`로 재배열한다 (`trainer/trainer.py:125-142`).

### 5.2 Patchify, layer alignment, dimension pooling

`PatchMaker`는 각 feature map에 `torch.nn.Unfold(kernel=patchsize, stride=1, padding=(patchsize-1)//2)`를 적용한다. 기본 patch size는 3이다. 각 layer의 patch grid가 다르면 첫 layer의 grid에 bilinear interpolation하여 정렬한다.

그 뒤 각 patch의 흐름은 다음과 같다.

```text
각 layer patch [B, P, C, k, k]
  → [B·P, C, k, k]
  → MeanMapper: flatten 후 adaptive average pool to target dimension
  → layer stack [B·P, L, D]
  → Aggregator: flatten(L·D) 후 adaptive average pool to D
  → feature embedding [B·P, D]
```

관련 구현은 `trainer/trainer.py:144-169`, `common.py:35-95`다. 코드 내 기본 SimpleNet 예시는 patch 수 10,368, input patch `[10368,512,3,3]`, MeanMapper 출력 `[10368,1536]`을 기록한다. 이 값은 batch/해상도/backbone에 따라 달라진다.

여기서 adaptive average pooling은 각 backbone layer가 서로 다른 channel 수와 patch 크기를 가져도, 마지막에는 모두 같은 길이 `D`의 feature vector로 맞추기 위한 장치다. 그래서 이후 score 모듈은 “이 feature가 layer2에서 왔는지 layer3에서 왔는지”보다 통일된 patch representation에 집중할 수 있다.

## 6. 공통 anomaly score와 anomaly map 생성

### 6.1 Base predict의 입력·출력

`Trainer._predict()` (`trainer/trainer.py:232-256`)은 method별 `_get_pred_scores(features)` 하나만 추상화하고 나머지를 공통으로 처리한다.

```text
embedding [B·P,D]
  → method score function
  → patch_scores [B·P] 또는 [B·P,1]
  → unpatch → [B,P] → [B,Hp,Wp]
  → RescaleSegmentor → anomaly map [B,masksize,masksize]

patch_scores [B·P,...]
  → unpatch → [B,P,...]
  → PatchMaker.score(): 마지막 channel 최대, patch 최대
  → image score [B]
```

`PatchMaker.score()` (`trainer/trainer.py:427-443`)은 차원이 2보다 클 동안 마지막 축 maximum을 취하고, 결과가 `[B,P]`이면 다시 patch 축 maximum을 취한다. 그러므로 기본 image-level score는 “가장 높은 patch anomaly”다. `top_k > 1`인 경우에만 상위 k patch 평균으로 바뀌지만, 이 코드의 기본 `top_k`는 0이므로 maximum 경로다.

`RescaleSegmentor` (`common.py:97-121`)은 patch grid를 `masksize×masksize`로 bilinear upsampling하고, 크기가 달랐던 경우에만 `scipy.ndimage.gaussian_filter(sigma=args.last_score_blur_sigma)`를 적용한다. 기본 sigma는 1.0이다. patch grid가 이미 target과 동일하면 smoothing 없이 그대로 반환한다.

bilinear upsampling은 작은 patch 격자를 큰 이미지 크기로 확대할 때 이웃 patch 값을 부드럽게 섞는 방법이다. Gaussian filter는 그 뒤의 점 잡음을 줄여 heatmap을 보기 쉽게 만든다. 둘 다 **새로운 이상 위치를 찾아내는 모델**은 아니며, 이미 계산된 patch score를 원래 이미지 위치에 표현하기 위한 후처리다.

### 6.2 SimpleNet과 PatchCore의 score source

| 방법 | patch score 원천 | 학습 시 보관/학습 대상 | image score |
|---|---|---|---|
| SimpleNet | `-discriminator(embedding)` | normal embedding과 synthetic noise를 분리하도록 discriminator 학습 | patch maximum |
| PatchCore | test patch와 normal memory-bank patch의 NN distance | train patch embedding → approximate greedy coreset → FAISS index | patch maximum |

SimpleNet은 `trainer/trainer_simplenet.py:49-61`에서 score를 음의 discriminator logit으로 만든다. PatchCore는 `trainer/trainer_patchcore.py:111-163`에서 train images의 embedding을 모아 coreset sampling한 뒤 FAISS nearest-neighbour scorer에 fit한다. `NearestNeighbourScorer.predict()`은 NN distances의 평균을 patch anomaly score로 반환한다 (`trainer/trainer_patchcore.py:203-221`). 이 저장소의 PatchCore config는 nearest neighbour 수 1이므로 결과적으로 각 patch의 nearest-memory distance다.

### 6.3 자체 후처리하는 방법

아래 방법은 base `_predict()`의 patch-score → `RescaleSegmentor` 경로를 그대로 쓰지 않는다.

| 방법 | anomaly map | image anomaly score | 핵심 코드 |
|---|---|---|---|
| RD / RD-Orig | encoder feature와 decoder feature의 layer별 `1-cosine_similarity`; 각 layer map을 interpolate하고 합산(`amap_mode='a'`), Gaussian sigma 4 | map maximum | `trainer/trainer_rd.py:131-166,199-219` |
| Dinomaly | encoder/decoder feature의 `cal_anomaly_maps` 결과; 256으로 resize 후 Gaussian kernel(5, sigma 4) | flatten map의 상위 1% 평균 | `trainer/trainer_dinomaly.py:150-191` |
| UniAD | model의 `output['pred']` | `max(avg_pool(pred,16×16))`, map mean, map std의 평균 | `trainer/trainer_uniad.py:152-184` |
| WinCLIP | CLIP normal/abnormal text similarity와 multi-scale token similarity를 harmonic aggregation | global class-token anomaly score(및 few-shot 보정) | `trainer/trainer_winclip.py:60-114` |
| PromptAD | prompt gallery와 image feature의 normal/abnormal similarity | prompt-based image score | `trainer/trainer_promptad.py:245` 이후 `predict()` |
| GLASS | 자체 `Trainer_GLASS.predict()` | 자체 score/map 경로 | `trainer/trainer_glass.py` |
| COAD | feature memory bank NN, attention/LOF 보정 및 별도 patch scorer | COAD 전용 aggregation | `COAD/COAD.py:430-516` |

따라서 서로 다른 방법의 “anomaly score”가 같은 수학적 스케일이라고 가정하면 안 된다. 비교 지표가 AUROC라면 각 방법 내부 ordering이 핵심이지만, absolute score threshold를 방법 간 공유하려면 별도 calibration이 필요하다.

표를 읽는 간단한 방법은 다음과 같다. PatchCore는 “정상 patch와의 거리”, RD는 “encoder와 decoder가 서로 복원하지 못한 정도”, CLIP 계열은 “정상/이상 문장과 이미지가 얼마나 닮았는지”를 점수로 쓴다. 모두 숫자가 커질수록 이상 쪽으로 해석하지만, 숫자가 나온 이유가 다르므로 `0.5`라는 동일한 threshold에 같은 의미를 부여할 수 없다.

## 7. 평가 전후처리와 산출물

### 7.1 평가 직전 정규화

공통 base `Trainer._evaluate()` (`trainer/trainer.py:329-377`)은 image score를 min–max normalization한 뒤 `metrics_gpu.compute_imagewise_retrieval_metrics()`의 binary AUROC에 넣는다. `pixel_auroc`가 활성화되거나 segmentation 이미지 저장을 요청하면 map도 `metrics_gpu.normalize_segmentations()`으로 정규화하여 pixel AUROC와 saliency F1을 구한다.

AUROC 자체는 score의 단조 변환에 불변이므로 일반적인 min–max normalisation은 image AUROC ranking을 바꾸지 않는다. 다만 score가 모두 동일하면 분모가 0이 될 수 있으며, 현재 코드에 별도 guard는 없다.

`metrics_gpu.normalize_segmentations()`은 이름과 달리 각 sample map을 독립적으로 정규화하지 않는다. loop의 각 sample min/max를 **전체 batch map tensor**에 적용한 뒤 평균한다. test loader가 batch size 1이므로 현재 기본 실행에서는 사실상 한 sample 정규화와 같지만, batch>1 evaluation으로 변경하면 의도한 per-image 정규화와 달라진다.

AUROC는 간단히 말해 “정상 이미지보다 이상 이미지에 더 높은 점수를 주는 순서가 잘 지켜졌는가”를 보는 지표다. 예를 들어 정상 세 장의 점수가 `0.1, 0.2, 0.3`, 이상 세 장의 점수가 `0.7, 0.8, 0.9`이면 순서가 완벽하므로 AUROC가 높다. 점수의 절대값보다 정상과 이상이 얼마나 잘 분리되어 정렬되는지가 중요하다. pixel AUROC도 같은 원리를 이미지 한 장이 아닌 모든 pixel에 적용한다.

### 7.2 최종 산출

`main_run.py`는 seed와 category별 metric을 DataFrame으로 모아 다음에 저장한다.

```text
<results_path>/<method>__<layers>_<csv_save_name>/results_<method>[...].csv
```

기본 metric naming은 `auroc_{min,max,mean,std}`, `pixel_auroc_{...}`, `pro_{...}`, `sal_f1_{...}`다. segmentation 이미지는 `save_segmentation_images=True`일 때 별도 output directory에 저장하며, 저장 전 map 전체의 min–max normalization과 image 역정규화를 수행한다 (`trainer/mixins.py:200-225`).

## 8. 재현·해석 시 확인할 항목

1. **실제 tensor 크기 확인**: `resize`, `imagesize`, `masksize`를 모두 log한다. BaseDataset의 활성 transform은 `resize`만 쓰므로 설정만 보고 shape를 추정하지 않는다.
2. **method별 score 정의 명시**: PatchCore distance, SimpleNet negative logit, RD cosine residual, Dinomaly top-1% mean, UniAD max/mean/std는 서로 교환 가능하지 않다.
3. **dataset variant 기록**: `glass`는 GLASS 전용 dataset/augmentation으로 registry가 자동 치환되므로 동일한 `mvtec` key라도 다른 preprocessing일 수 있다.
4. **pixel metric 유효성 확인**: LG처럼 pixel mask가 없는 dataset에서는 pixel AUROC는 의미가 없거나 -1이 된다. MVTec test mask 경로가 실제 파일과 정렬되는지도 확인한다.
5. **validation의 용도 분리**: 현재 MVTec `VAL`은 별도 validation directory가 아니라 test images의 1%이며 mask를 읽지 않는다. model selection 용도로 쓰려면 split 구현을 보완해야 한다.

## 9. 코드의 함수 주석을 읽는 법

이번 분석 대상의 모든 Python 함수에는 실행 코드를 바꾸지 않고 한국어 주석을 덧붙였다. 함수 바로 아래의 주석은 아래 순서로 읽으면 된다.

```python
# 역할: 이 함수가 전체 프로그램에서 담당하는 한 가지 일
# 매개변수: 함수에 넣어야 하는 값과 선택 가능한 설정
# 반환값: 실행이 끝난 뒤 호출자에게 돌려주는 값
# 상세 흐름: 내부에서 중요한 함수·모듈을 어떤 목적으로 호출하는지
# 처리 순서: 조건 분기, 반복, 상태 갱신, 결과 반환의 순서
```

예를 들어 `Trainer._predict(images)`를 볼 때는 먼저 **입력 이미지가 들어온다**는 사실을 확인하고, 다음으로 embedding을 추출한다는 `상세 흐름`을 읽는다. 이어서 patch별 score를 만든 뒤 patch grid로 되돌리고, 마지막에 image score와 anomaly map을 반환한다는 `처리 순서`를 따라가면 된다. 초보자는 함수 본문을 한 줄씩 모두 해석하려 하기보다, 이 다섯 줄의 주석으로 목적과 입출력을 먼저 잡은 뒤 아래 코드에서 해당 단계만 확인하는 편이 좋다.

### 9.1 특히 먼저 읽을 함수

| 목표 | 먼저 볼 함수 | 다음으로 연결되는 함수 |
|---|---|---|
| 데이터 한 장이 어떻게 준비되는지 | `BaseDataset.__getitem__` | `BaseDataset.transform_image`, dataset별 `get_image_data` |
| batch가 만들어지는 과정 | `main_dataset.create_dataloaders` | PyTorch `DataLoader` |
| backbone feature가 되는 과정 | `Trainer._embed` | `NetworkFeatureAggregator.forward`, `PatchMaker.patchify` |
| 공통 score/map의 출발점 | `Trainer._predict` | method별 `_get_pred_scores`, `RescaleSegmentor.convert_to_segmentation` |
| PatchCore의 거리 점수 | `PatchCore._get_pred_scores` | `NearestNeighbourScorer.predict` |
| Dinomaly의 map과 image score | `Dinomaly._predict` | `cal_anomaly_maps` |

이 연결은 “함수 하나를 완전히 외운 뒤 다음 파일로 넘어간다”는 뜻이 아니다. `역할 → 매개변수 → 반환값 → 상세 흐름`만 읽고, 표의 오른쪽 함수로 이동해 같은 방법으로 추적하면 전체 호출 흐름을 잃지 않는다.

## 10. 초보자가 가장 자주 막히는 여덟 가지

### 10.1 Tensor 옆의 shape는 어떻게 읽는가?

`shape`는 tensor 안에 든 숫자를 설명하는 **상자 크기 표기**다. 예를 들어 이미지 tensor의 `[B, C, H, W]`는 다음을 뜻한다.

| 기호 | 뜻 | 예: `[4, 3, 288, 288]` |
|---|---|---|
| `B` | 한 번에 처리하는 이미지 수(batch) | 이미지 4장 |
| `C` | 색상 채널 | RGB 3개(R, G, B) |
| `H` | 이미지 높이(pixel) | 288 pixel |
| `W` | 이미지 너비(pixel) | 288 pixel |

따라서 `[4, 3, 288, 288]`은 “288×288 RGB 이미지 4장”이다. mask의 `[4, 1, 224, 224]`은 “각 이미지의 위치마다 정상=0, 결함=1을 기록한 흑백 지도 4장”이다. feature의 `[B, C, H, W]`도 표기는 같지만, `C`는 RGB가 아니라 모델이 뽑아낸 특징 종류 수다. shape만 보고도 **이미지 몇 장인지, 공간 크기가 얼마인지, 색/특징 채널이 몇 개인지**를 먼저 확인하면 된다.

### 10.2 Batch란 무엇인가?

batch는 “모델에게 한 번에 건네는 이미지 묶음”이다. 사진 100장을 한 장씩 100번 계산할 수도 있지만, GPU는 여러 장을 한꺼번에 계산하는 데 강하다. 그래서 DataLoader가 예를 들어 이미지 4장을 모아 `[4, 3, 288, 288]`으로 만든다. 이 4장이 batch다.

여기서 batch는 이미지들을 섞어 한 이미지로 만드는 것이 아니다. 모델은 4장을 병렬로 처리할 뿐, 결과 score도 `[4]`처럼 이미지별로 따로 남는다. 이 저장소의 평가 test loader는 기본적으로 batch size가 1이어서 한 장을 평가하고 결과를 기록한 뒤 다음 이미지로 넘어간다.

### 10.3 Defect mask가 없어도 image AUROC는 어떻게 계산하는가?

mask는 “결함이 이미지의 **어느 pixel**에 있는가”를 알려 주는 정답이다. 반면 image AUROC에 필요한 것은 이미지마다 정상인지 이상인지를 나타내는 **한 개의 정답 label**뿐이다.

```text
이미지 A: good 폴더에 있음       → is_anomaly = 0, model score = 0.12
이미지 B: scratch 폴더에 있음    → is_anomaly = 1, model score = 0.83
```

이처럼 `BaseDataset.__getitem__()`은 폴더명으로 `is_anomaly`를 만든다. `Trainer._evaluate()`는 모든 이미지의 `is_anomaly`와 image-level anomaly score를 모아, 이상 이미지가 정상 이미지보다 높은 점수를 받도록 잘 정렬됐는지 AUROC를 계산한다. mask가 없어도 된다. 다만 **pixel AUROC**는 “어느 pixel이 결함인가”가 필요하므로 mask가 없으면 계산할 수 없거나 의미가 없다.

### 10.4 Image와 mask의 크기가 다르면 어떻게 하는가?

이 저장소는 image와 mask를 의도적으로 다른 목표 크기로 변환할 수 있다. 예를 들어 image는 backbone 입력용 `288×288`, mask는 평가용 `224×224`가 될 수 있다. 둘을 곧바로 pixel끼리 뺄셈하거나 비교하지 않기 때문에 이것만으로 오류가 나지는 않는다.

처리 방식은 다음과 같다.

```text
image  → 모델 입력 크기로 resize → feature / patch score 생성
patch score → RescaleSegmentor가 masksize(예: 224×224)로 확대 → anomaly map
mask   → 처음부터 같은 masksize(224×224)로 resize
anomaly map과 mask → pixel AUROC 비교
```

즉, **비교가 필요한 마지막 순간에는 map과 mask가 같은 크기**가 되도록 맞춘다. image AUROC는 이미지당 score 한 개만 비교하므로 image와 mask의 가로세로 크기가 아예 관계없다.

### 10.5 일반 MVTec Dataset과 GLASS 전용 MVTec Dataset은 무엇이 다른가?

둘 다 원래 MVTec 폴더 구조와 test ground-truth mask를 읽는다. 그러나 GLASS는 학습 중 정상 이미지에 인공 결함을 만들어 학습하는 논문 방법이므로, 일반 Dataset보다 많은 학습용 재료가 필요하다.

| 항목 | 일반 `datasets/mvtec.py` + `datasets/base.py` | GLASS 전용 `trainer/GLASS_lib/mvtec.py` |
|---|---|---|
| 기본 목적 | 원본 MVTec 이미지를 공통 형식으로 제공 | GLASS의 인공 이상 학습을 위한 입력 생성 |
| 학습 transform | 공통 resize/tensor 변환 중심 | resize·center crop·정규화와 선택적 random augmentation |
| 학습용 추가 데이터 | 원본 image, 기본 mask/foreground | 외부 anomaly-source 이미지, Perlin mask, foreground mask |
| 추가 반환값 | 공통 sample dict | `aug`, `mask_s`, `mask_gt` 등을 더 반환 |
| 인공 결함 생성 | 없음 | Perlin mask 영역에 anomaly-source 이미지를 섞어 `aug_image` 생성 |

그래서 설정에서 dataset 이름이 둘 다 `mvtec`여도 method가 `glass`이면 registry가 GLASS 전용 클래스로 바꾼다. 이 차이는 평가의 정답 mask를 바꾸려는 것이 아니라, **GLASS 학습 방식이 요구하는 합성 결함 입력을 만들기 위한 차이**다.

### 10.6 “11개 방법”은 무엇인가?

이는 이 실행 프레임워크에서 `method:` 설정값으로 선택할 수 있는 **11개의 이상 탐지 알고리즘 구현**을 뜻한다. 한 모델 안에 11개가 동시에 들어 있는 것이 아니다. 실행할 때 하나를 고른다.

`coad`, `dinomaly`, `glass`, `padim`, `patchcore`, `promptad`, `rd`, `rd_orig`, `simple`, `uniad`, `winclip`이 그 11개다. 예를 들어 `method: patchcore`면 PatchCore trainer가 만들어지고, `method: simple`이면 SimpleNet trainer가 만들어진다. 모두 “이미지가 정상인가 이상인가, 이상이면 어디인가”를 풀지만, feature를 비교하거나 score를 만드는 방법이 서로 다르다.

### 10.7 코드에서 말하는 ‘계약(contract)’은 무엇인가?

여기서 계약은 법적 문서가 아니라 **서로 다른 코드가 약속한 입출력 규칙**이다. 예를 들어 DataLoader가 어느 Dataset을 쓰든 아래 key를 준다는 약속이 있다.

```text
sample['image']      : 모델에 넣을 이미지 tensor
sample['mask']       : pixel-level 정답 mask(없으면 0 mask)
sample['is_anomaly'] : image-level 정답(정상 0 / 이상 1)
```

또한 runner는 어느 Trainer를 선택하든 `load()`, `train()`, `predict()`, `get_evaluation_metrics()`를 호출할 수 있다는 약속을 사용한다. 이 약속 덕분에 `main_run.py`는 PatchCore의 memory bank나 SimpleNet의 discriminator를 직접 알 필요 없이 같은 실행 흐름을 유지한다. 계약을 어기면, 예를 들어 Dataset이 `image` key를 주지 않거나 Trainer가 `predict()`를 제공하지 않으면 교체가 실패한다.

### 10.8 PatchMaker는 모델인가?

아니다. `PatchMaker`는 학습하는 신경망 모델이 아니라, feature map을 patch 단위로 자르고 결과를 다시 배열하는 **보조 도구 class**다.

예를 들어 backbone feature가 `[1, 512, 36, 36]`이면 PatchMaker는 `3×3`처럼 작은 창을 feature map 위로 움직여 여러 feature patch를 만든다. 각 patch는 “원본 이미지의 이 작은 주변 영역을 나타내는 특징”이 된다. PatchCore와 SimpleNet은 이 patch마다 anomaly score를 만든다. 이후 PatchMaker는 patch score들을 `[한 이미지, patch 행, patch 열]` 격자로 되돌리고, 그중 가장 높은 score를 image score 후보로 고른다.

```text
feature map → PatchMaker가 겹치는 작은 feature patch들로 분할
            → 방법별 score 계산(한 patch당 숫자 하나)
            → patch score 격자로 복원
            → 가장 큰 patch score = image-level anomaly score
```

따라서 PatchMaker는 “결함을 판정하는 두뇌”가 아니라, 결함 점수를 **어느 위치의 점수인지 보존하면서** 만들고 되돌리는 자르는 도구다.
