## 한 줄 결론

현재 공통 프레임워크는 `validation`이라는 이름의 로더를 만들지만, 일반 MVTec 구현에서는 **정상 train 이미지를 나눈 검증셋이 아니다.** `VAL`도 `test/` 경로를 읽도록 되어 있고, `bottle`처럼 각 결함 유형의 이미지 수가 100장보다 적으면 `1%` 축소 과정에서 검증 샘플이 전부 0장이 된다. 따라서 학습 epoch·backbone layer·prompt·threshold를 고를 때 사용할, **test와 분리된 정상 검증 근거가 없다.**

제안은 두 단계다.

1. MVTec `train/good`만 seed 고정으로 train/normal-validation으로 나누고, test에는 최종 1회만 접근한다.
2. 정상 validation 이미지에 국소 합성 이상을 만들고 후보 설정을 고르는 SWSA(Selection With Synthetic Anomalies) 계열 검증을 적용한다. 이 방법은 실제 결함 라벨 없이도 후보 설정의 순위를 만들 수 있다 [2].

이는 아직 구현·실험하지 않은 **개선 가설**이다. 아래 코드는 현재 구조의 근거이고, 성능 개선 수치는 아직 없다.

## 구현 상태

정상 validation을 만드는 **데이터 분할 단계는 구현하고 실제 `bottle` 데이터로 검증했다.** 합성 이상 생성·후보 선택 adapter와 trainer의 epoch 선택 규칙은 아직 구현하지 않았다.

## 1. 문제 정의

산업 이상 탐지는 보통 정상 이미지만 학습에 쓴다. 그래서 “몇 epoch에서 멈출지”, “어느 layer를 쓸지”, “어느 prompt가 나은지”를 정할 때 실제 이상 test 라벨을 보면 안 된다. 그 라벨은 배포 때 존재하지 않으며, 마지막 성능을 공정하게 확인하는 용도이기 때문이다.

여기서 필요한 것은 다음 세 데이터 집합이다.

```text
train_normal       모델 학습용 정상 이미지
validation_normal  설정 선택용 정상 이미지 + 여기서 만든 합성 이상 이미지
test               마지막 1회 평가용 정상/실제 이상 이미지와 정답 마스크
```

현재 코드는 첫 번째와 세 번째는 만들지만, 두 번째를 올바르게 만들지 못한다.

## 2. 코드에서 확인한 한계

### 2.1 수정 전: `VAL`이 train이 아니라 test 폴더를 읽었다

[`datasets/mvtec.py`](../../method9/source/common_framework_validation_patch/framework_snapshot/datasets/mvtec.py)의 37–38행은 split이 `TRAIN`일 때만 `train`을 읽고, 그 외에는 모두 `test`를 읽는다.

```python
classpath = os.path.join(
    self.source, classname,
    "train" if self.split == DatasetSplit.TRAIN else "test"
)
```

따라서 `DatasetSplit.VAL`은 정상 train 이미지가 아니라 MVTec의 test 경로를 대상으로 한다. `main_dataset.py` 120–128행은 실제로 이 `VAL` 객체를 validation dataset으로 만든다.

```text
main_dataset.py
  validation_dataset(split=VAL, subtest=True)
       ↓
mvtec.py
  VAL != TRAIN → <class>/test/* 를 탐색
```

### 2.2 수정 전: 설정값은 있으나 정상 train/validation 분할 코드는 꺼져 있었다

`main.py`의 기본 `train_val_split`은 `1.0`이다. 더 중요한 점은 [`datasets/mvtec.py`](../../method9/source/common_framework_validation_patch/framework_snapshot/datasets/mvtec.py) 54–64행의 train/validation 분할 코드 전체가 주석 처리되어 있다는 것이다.

즉 `train_val_split=0.9`처럼 값을 바꿔도 현재 일반 MVTec 구현은 정상 train 이미지의 90%/10% 분할을 수행하지 않는다.

### 2.3 수정 전: `bottle`의 validation은 빈 로더가 됐다

`main_dataset.py`는 validation에 `subtest=True`를 전달한다. [`datasets/mvtec.py`](../../method9/source/common_framework_validation_patch/framework_snapshot/datasets/mvtec.py) 89–90행은 **결함 유형별로** 이미지 수의 1%를 남긴다.

```python
data_to_iterate_class = data_to_iterate_class[:int(len(data_to_iterate_class) * 0.01)]
```

`bottle`의 `good`은 20장이고, 각 결함 유형도 100장 미만이다. 따라서 `int(20 × 0.01) = 0`이며 각 그룹이 0장이 된다. 이후 [`main_dataset.py`](../../method9/source/common_framework_validation_patch/framework_snapshot/main_dataset.py)에서 비어 있는 validation dataset은 `None` loader로 바뀐다.

```python
validation_loader = None
if validation_dataset.data_to_iterate:
    validation_loader = _make_loader(...)
```

### 2.4 남은 한계: 일부 학습기는 전달된 `val_data`를 아직 사용하지 않는다

공통 lifecycle은 `trainer.train(training, validation, testing, dataset_name)` 형태로 세 로더를 전달한다. 하지만 RD, Dinomaly, UniAD의 `train(...)` 본문은 `val_data`를 참조하지 않고, `epoch_test_mode=1`일 때 `test_data`의 `is_anomaly`, `mask`로 AUROC와 F1을 계산한다.

예를 들어 [`trainer/trainer_rd.py`](../../method9/source/common_framework_validation_patch/framework_snapshot/trainer/trainer_rd.py) 111–136행은 epoch마다 `predict(test_data)`와 `_evaluate(...)`를 호출하고 마지막 5 epoch의 test metric 평균을 결과로 쓴다. Dinomaly와 UniAD도 같은 패턴이다.

```text
RD/Dinomaly/UniAD, epoch_test_mode=1
  매 epoch: test image → anomaly score/map
             + test label/mask → AUROC, Pixel AUROC, F1
  마지막 5 epoch의 test metric 평균 → 보고 결과
```

이는 test label을 gradient에 직접 넣는 학습은 아니다. 하지만 epoch 수, config, checkpoint를 사람이 이 로그로 조정하면 **test set에 맞춘 간접 선택(test leakage)** 이 된다.

## 3. 이 한계가 현재 결과에 의미하는 범위

W40의 전체 method `bottle` 실행은 기본값 `epoch_test_mode=0`으로 1회 실행했고, test AUROC가 높은 epoch를 골라 재실행하지 않았다. 따라서 그 한 번의 결과 자체를 “이 코드 때문에 이미 무효”라고 말할 근거는 없다.

다만 다음 작업부터는 문제가 된다.

- `epoch_test_mode=1`로 학습 곡선을 보고 좋은 epoch를 고르는 경우
- layer, image size, prompt, threshold, synthetic anomaly 설정을 여러 번 바꾸고 test AUROC가 가장 높은 설정을 채택하는 경우
- GLASS처럼 학습 중 test metric을 반복 계산하는 구현을 공통 비교에 포함하는 경우

현재처럼 11개 방법을 하나의 framework에서 비교하려면, 각 방법이 test에 접근하는 시점을 동일하게 제한해야 한다.

## 4. 원인 가설

### H1. 정상 전용 validation이 없어서, 설정 선택이 실제 이상 test로 밀려난다

정상 데이터만 있는 이상 탐지에서는 일반 분류처럼 validation AUROC를 바로 계산할 수 없다. 현재 dataset 코드가 정상 holdout을 만들지 않고, trainer도 `val_data`를 공통 계약으로 사용하지 않으므로, 개발자는 성능을 확인하기 위해 test AUROC/Pixel AUROC를 반복해서 보게 된다.

H1이 맞다면 다음 현상이 관찰되어야 한다.

- test metric으로 선택한 설정과, test를 보지 않은 합성 validation으로 선택한 설정이 자주 다르다.
- 전자를 기준으로 한 test 성능은 반복적인 config 탐색 횟수가 늘수록 낙관적으로 변한다.
- 고정한 실제 test에서 평가할 때, 합성 validation의 후보 순위와 실제 순위가 양의 상관을 보인다. 상관이 낮으면 합성 방식도 개선해야 한다.

## 5. 기존 연구에 근거한 개선안

### 5.1 정상 holdout과 test 분리: MVTec AD 2의 평가 절차

MVTec AD 2는 학습과 validation을 모두 정상 데이터로 제공하고, **정상 validation으로 학습 기간·threshold 같은 hyperparameter를 정한 후** private test에는 추론 결과만 제출하도록 한다 [1]. private test의 정답을 숨기는 이유도 반복 tuning에 의한 과적합을 막기 위해서다.

이 프레임워크에도 같은 분리를 먼저 적용한다.

| 단계 | 입력 | 허용되는 정보 | 금지되는 정보 |
|---|---|---|---|
| 학습 | `train_normal` | 정상 이미지 | 실제 이상 이미지·mask |
| 선택 | `validation_normal` + 합성 이상 | 합성 이미지의 생성 mask | MVTec test label·mask |
| 최종 평가 | `test` | 모델의 score/map | test 결과로 다시 config 변경 |

### 5.2 후보 선택: SWSA의 합성 이상 validation

Fung 등은 정상 support 이미지로 합성 이상을 생성해 validation set을 만들고, 그 합성 set의 AUROC로 anomaly detector 또는 CLIP prompt 후보를 고르는 **SWSA**를 제안했다 [2]. 합성 이상은 별도 실제 결함 라벨, fine-tuning, 외부 결함 데이터 없이 만들 수 있다.

이 공통 framework에는 SWSA의 전체 diffusion 파이프라인보다, 먼저 **국소 CutPaste형 합성 이상**을 적용하는 것이 현실적이다.

```text
validation_normal 이미지 x
   ├─ 원본 x : label=0, mask=0
   └─ x의 작은 patch를 잘라 다른 위치에 붙인 x~ : label=1, 합성 patch mask=1
                                      ↓
각 후보 (epoch / layer / prompt / image size)가 x와 x~의 score/map 생성
                                      ↓
합성 Image AUROC + 합성 Pixel AUROC으로 후보 1개 선택
                                      ↓
선택을 잠근 뒤 실제 test를 단 한 번 평가
```

SWSA는 실제 미세 산업 결함이 합성 결함보다 정상 분포에 더 가깝기 때문에 산업 데이터에서 선택이 어려울 수 있음을 함께 보고한다 [2]. 그러므로 이 제안은 “합성 validation AUROC가 실제 AUROC를 완벽히 대체한다”는 주장이 아니라, **test label을 쓰는 것보다 배포 조건에 가까운 선택 기준을 만들자**는 제안이다.

   - validation에는 `good` 이외 폴더가 섞이지 않게 했다.
2. `main_dataset.py` **완료**
   - `subtest=True` 1% 절단 대신, 위의 정상 validation loader를 만든다.

3. 공통 선택 adapter (새 모듈) **미구현**
   - validation normal로 원본/합성 이상 쌍과 합성 mask를 생성한다.
   - 모든 method의 기존 `predict` 결과(score/map)를 받아 합성 AUROC를 계산한다.
   - 후보 선택과 test 평가를 분리해 기록한다.
4. 우선 적용 범위
   - 여러 epoch를 학습하는 RD, Dinomaly, UniAD, SimpleNet부터 적용한다.
   - PatchCore/PaDiM은 epoch checkpoint 대신 layer·coreset·image size 후보 선택에 쓴다.
   - WinCLIP/PromptAD/AnomalyCLIP은 prompt 후보 선택에 쓴다.

## 8. 현재 판단

가장 먼저 고쳐야 할 것은 detector의 feature extractor가 아니라 **선택 데이터의 계약**이다. 정상 validation을 만들지 않은 상태에서 test metric을 반복 관찰하면, 새 방법의 개선인지 test-set 맞춤인지 구분할 수 없다.

따라서 다음 구현은 “새 anomaly score를 추가”하는 것보다, 정상 holdout + 합성 이상 validation + final-test-once 규칙을 공통 framework에 추가하는 것이 타당하다. 이후 합성 validation이 실제 결함 유형을 제대로 대표하지 못한다는 evidence가 나오면, CutPaste형 합성 대신 GLASS의 texture 합성 또는 domain-specific defect synthesis를 다음 후보로 비교한다.

| 합성 이상으로 label-free 선택 | [SWSA 논문](https://clementfung.me/gallery/papers/tai25-swsa.pdf) | 후보 선택의 구체적 방법 |

## 10. 실제 코드 수정 과정과 검증 결과 (2026-09-28)

### 10.1 수정 전 데이터 흐름

```text
MVTec train/good 209장 → TRAIN 209장
MVTec test 83장       → TEST 83장
VAL                   → test 경로의 유형별 1% → bottle에서는 0장
```

`VAL`은 실질적으로 비어 있었고, train의 정상 이미지를 따로 보관하지 않았다.

### 10.2 적용한 코드 변경

| 파일 | 변경 내용 | 목적 |
|---|---|---|
| `datasets/base.py` | constructor가 받은 `seed`를 `self.seed`에 보관 | 같은 실행 조건에서는 같은 train/validation 분할을 재현 |
| `datasets/mvtec.py` | `VAL`도 `train`을 읽게 변경 | validation이 test 파일을 읽지 않게 함 |
| `datasets/mvtec.py` | `good` 파일 목록을 seed 고정 shuffle 뒤 90%/10%로 분할 | train과 validation이 겹치지 않도록 정상 이미지를 배분 |
| `datasets/mvtec.py` | validation에는 `good` 이외 유형을 제외 | 실제 결함·정답 mask가 validation에 들어가지 않게 함 |
| `main_dataset.py` | validation 생성 시 `train_val_split`을 전달하고 `subtest=False`로 변경 | 1% 축소가 아니라 정상 validation 전체를 DataLoader로 생성 |
| `main.py` | 기본 `train_val_split`을 `1.0`에서 `0.9`로 변경 | 기본 실행에서도 validation을 생성 |

분할은 아래 규칙을 따른다.

```text
seed=0, train_val_split=0.9

train/good 209장
  → 고정 순서로 섞기
  → 188장: training DataLoader
  →  21장: validation DataLoader

test 83장
  → 변경 없음: testing DataLoader
```

`train_val_split=1.0`을 설정하면 기존 실행과 호환되게 train 209장, validation 0장으로 동작한다.

### 10.5 아직 바꾸지 않은 부분

이번 변경은 validation **데이터를 올바르게 만들고 전달하는 단계**다. RD·Dinomaly·UniAD 등의 trainer가 정상 validation을 사용해 epoch를 자동 선택하도록 바꾸지는 않았다.

그 기능을 바로 추가하지 않은 이유는 validation이 정상 이미지뿐이기 때문이다. 정상 validation으로는 오탐과 score 분포를 확인할 수 있지만, 실제 결함 탐지 AUROC를 계산할 수는 없다. 합성 이상 validation 또는 별도 semi-supervised validation의 선택 기준을 먼저 정한 뒤, trainer별 선택 로직을 추가해야 한다.
