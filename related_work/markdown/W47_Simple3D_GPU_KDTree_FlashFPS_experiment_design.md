# W47 Simple3D — GPU KD-tree·FlashFPS 실험별 교체 범위

**GPU KD-tree는 이웃을 찾는 방법이고, FlashFPS는 중심점을 고르는 방법임.** 서로 대체하는 기술이 아님. 최종 실험에서는 GPU KD-tree를 유지한 채 **특징 집계용 FPS만** 바꿨으며, 점수 평활화용 FPS는 기존 방식으로 유지함.

## 1. Simple3D에서 어느 단계인가?

| 순서 | 단계 | 하는 일 | 변경 관계 |
|---|---|---|---|
| 1 | 법선 계산 | 각 점 주변의 표면 방향을 계산함 | 아래 기본 비교에서는 CPU Open3D 유지 |
| 2 | FPFH용 이웃 탐색·특징 계산 | 각 점 주변의 형상을 숫자 특징으로 표현함 | GPU KD-tree 경로에서는 원래 CPU FPFH 구간을 **CuPy GPU KD-tree 조회 + CUDA SPFH/FPFH 계산**으로 교체 |
| 3 | 특징 집계 중심점 선택 | 주변 특징을 모을 기준점 4,096개를 고름 | **FlashFPS 실험의 교체 대상**. 기존 PointNet2 CUDA FPS와 비교 |
| 4 | 특징 집계 이웃 탐색 | 선택한 중심점마다 가까운 128개 점의 특징을 모음 | 전체 GPU KD-tree판에서 기존 `KNN_CUDA`를 GPU KD-tree 조회로 교체 |
| 5 | 메모리뱅크 비교·보간 | 특징을 정상 특징과 비교하고 점수를 원본 점군에 퍼뜨림 | `torch.cdist/min`과 기존 정렬 기반 보간 유지. KD-tree로 교체하지 않음 |
| 6 | 점수 평활화 | 중심점 1,024개를 고르고 주변 12개 점의 점수를 모아 다시 보간함 | **중심점 선택(FPS)**과 **12-NN 조회**는 별개. 전체 GPU KD-tree판은 12-NN만 교체하고, 최종 혼합판도 평활화 FPS는 기존 방식 유지 |

GPU FPFH 경로는 각 점의 **120개 최근접 이웃**을 한 번 조회하고, 그 목록의 앞 40·80·120개를 스케일별 계산에 재사용함. 이때 FPFH 자체는 CUDA 커널이 계산하며, KD-tree는 이웃 인덱스만 제공함. 기본 특징 결합은 기존과 같이 40·80·80·120으로 132차원을 유지함.

### 중심점 4,096개와 이웃 16개·128개는 무엇이 다른가?

캡슐의 긁힘을 찾는다고 생각하면, **중심점 4,096개는 표면에서 ‘어디를 볼지’ 정하는 기준 위치의 수**임. FPS가 이 위치들을 고름. 그다음 **이웃 16개·128개는 각 위치에서 ‘주변 점을 몇 개 모을지’** 정하는 수임. Simple3D는 중심점마다 가까운 점의 FPFH 특징을 평균함. 128개를 쓰면 16개를 쓸 때보다 더 많은 점의 특징을 모으지만, 실제 거리 범위는 점의 밀도에 따라 달라짐.

| 실험 | 중심점 수 | 중심점당 집계 이웃 수 | 비교 목적 |
|---|---|---|---|
| 논문 기본 설정 | 별도 설정 | **128개** | 기본 성능 평가 |
| 논문 Figure 6 위쪽 | **256~8,192개**로 변경 | **16개**로 고정 | 중심점 수의 영향 확인 |
| 논문 Figure 6 아래쪽 | **4,096개**로 고정 | **8~128개**로 변경 | 이웃 수의 영향 확인 |
| 우리 최종 GPU KD-tree vs FlashFPS | **두 버전 모두 4,096개** | **두 버전 모두 128개** | 중심점 선택 방식만 비교 |

즉, 논문의 **16개는 중심점 수만 바꿔 보기 위한 실험 조건**임. 우리 실험에서 FlashFPS를 써도 원본 점군에서 FPFH를 계산하고, 선택한 각 중심점 주변의 128개 점을 조회하는 방식은 유지함. FPFH의 **40·80·120**과 점수 평활화의 **12개** 역시 집계 이웃 수와는 다른 단계의 숫자임. [Simple3D 논문 — Experimental Setups·Figure 6](https://arxiv.org/html/2507.07435) · [캡슐의 별도 16개 vs 128개 비교](../../method12/markdown/W46_Simple3D_capsule_GPU_KDTree_k16_vs_k128.md)

## 2. GPU KD-tree 실험: 어떤 조회를 바꿨는가?

| 버전 | FPFH용 이웃 탐색·계산 | 특징 집계 128-NN | 점수 평활화 12-NN | 두 단계의 FPS |
|---|---|---|---|---|
| **O · 공식 호환판** | CPU Open3D | 기존 `KNN_CUDA` | 기존 `KNN_CUDA` | 기존 PointNet2 CUDA FPS |
| **F · FPFH-only** | GPU KD-tree + CUDA FPFH | 기존 `KNN_CUDA` | 기존 `KNN_CUDA` | 기존 PointNet2 CUDA FPS |
| **G · 전체 GPU KD-tree** | GPU KD-tree + CUDA FPFH | GPU KD-tree | GPU KD-tree | 기존 PointNet2 CUDA FPS |

- **O ↔ G:** 52개 카테고리에서 두 버전을 재측정함. FPFH 계산 경로와 두 좌표 이웃 조회를 함께 바꾼 비교라, 이 차이를 KD-tree 조회 하나의 효과라고 볼 수 없음. O는 경로·장치 호환 오류 등을 보완한 버전이며 공식 코드를 그대로 실행한 버전이라는 뜻은 아님.
- **O ↔ F:** FPFH 구간만 바꾼 비교임. GPU 이웃 조회와 CUDA FPFH 계산이 함께 바뀌었으므로 두 효과를 분리하지 않음.
- **F ↔ G:** GPU FPFH를 공통으로 쓰되, 집계·평활화의 좌표 이웃 조회까지 GPU KD-tree로 바꾼 버전과 비교함. F는 기존 집계 조회의 4,000+96 배치와 FPFH 바깥 코드를 보존함. G는 통합 경로에서 트리·GPU 좌표를 재사용하므로, 시간 차이는 조회 커널만의 차이가 아님. F는 별도 시점에 실행하고 O/G는 기존 측정값을 참조함.
- **캡슐 이웃 수·스케일 실험:** G와 기존 FPS를 유지한 상태에서 집계 이웃을 128→16개로 줄이거나, 집계 16개를 유지한 채 FPFH 스케일을 20·40·60 또는 60·100·140으로 바꾼 실험임. FlashFPS로 교체한 실험과 구분함.

## 3. FlashFPS 실험: 어느 FPS를 어떻게 바꿨는가?

### 최종판에서 기존 GPU KD-tree판과 달라진 한 곳

**FlashFPS가 겨냥한 병목은 ‘중심점 선택’이지 ‘중심점당 128개 특징 모으기’가 아님.** MiniShift에서 중심점 선택은 **859.43 → 111.57ms**로 줄었지만, 별도 단계인 128-NN 조회는 **51.26 → 47.29ms**로 측정됐으며 조회 알고리즘과 이웃 수는 그대로였음. 더 오래 걸린 **FPFH용 전체 점 120-NN 조회(기존 1,237.26ms)**도 변경하지 않았음. 즉, 전체에서 가장 느린 단계를 바꾼 것이 아니라, 기존판에서 시간이 많이 들던 FPS를 줄인 것임.

기존 GPU KD-tree판도 **중심점을 고를 때는 KD-tree가 아니라 PointNet2 CUDA FPS**를 썼음. 최종판은 특징 집계용으로 `fps(dense, 4096)`을 호출할 때 **4,096개를 고르는 규칙만** 바꿈. KD-tree로 이웃을 찾는 코드는 양쪽에서 똑같이 사용함.

| 실제 처리 순서 | 기존 GPU KD-tree판 | 최종 FlashFPS 혼합판 |
|---|---|---|
| ① FPFH 계산 | 원본 점군에서 GPU KD-tree로 이웃을 찾고 CUDA로 FPFH 계산 | **그대로.** 원본 점군 전체에 대해 계산 |
| ② 특징 집계 중심점 선택 | 원본 전체에서 4,096개를 기존 FPS로 하나씩 고름 | **여기만 교체.** 원본에서 후보 25%를 시드 42로 뽑고, 그중 2,048개는 기존 FPS로 고름. 나머지 2,048개는 같은 후보 집합의 미선택 점을 원래 인덱스 순서대로 채움 |
| ③ 중심점 주변 특징 집계 | 중심점마다 원본 전체에서 가까운 128개를 GPU KD-tree로 찾고 그 특징을 평균 | **조회 방식과 128개는 그대로.** 다만 ②에서 고른 중심점 위치가 달라지면 실제로 찾는 이웃과 집계 특징도 달라질 수 있음 |
| ④ 점수 평활화 | 원본 전체에서 기존 FPS로 1,024개를 고르고, GPU KD-tree로 각각 주변 12개 조회 | **그대로.** 평활화용 FPS에는 FlashFPS를 적용하지 않음 |

예를 들어 MiniShift 한 샘플의 원본 점이 50만 개라면, 기존판은 특징 집계용 FPS의 후보로 **50만 개 전부**를 보고 4,096개를 직접 고름. 혼합판은 **12만 5천 개만** 비교 대상으로 두고 **2,048번만** FPS로 고름. 최종 중심점 수는 여전히 4,096개임. 이렇게 줄인 것은 **중심점 선택의 후보 수와 FPS 반복 수**이지, KD-tree가 조회하는 원본 점의 수나 집계 이웃 128개가 아님.

코드에서 보면 [GPU KD-tree 경로](../../method12/source/simple3d_gpu_kdtree.py)는 FPS가 반환한 중심점을 받아 128-NN을 조회함. 최종 샘플링 코드 (로컬 기록)는 **4,096개 요청만** 위 방식으로 처리하고, **1,024개 요청은** 기존 FPS에 그대로 넘김.

### 캡슐에서 확인한 변형과 최종 설정

아래는 **모두 G의 GPU KD-tree·CUDA FPFH와 함께 사용**함. FPS 후보를 25%로 줄였다는 말은 **중심점 선택에 들어가는 후보만** 줄였다는 뜻임. FPFH나 주변 이웃 조회의 원본 점군까지 25%로 줄인 것은 아님.

| 실험                | 특징 집계: 최종 4,096개를 고르는 방법                            | 점수 평활화: 최종 1,024개를 고르는 방법              | 바로 앞에서 확인한 변경                       |
| ----------------- | --------------------------------------------------- | -------------------------------------- | ----------------------------------- |
| G 기준              | 전체 점군에서 전부 기존 FPS로 선택                               | 전체 점군에서 전부 기존 FPS로 선택                  | 기준선                                 |
| 캡슐 · 앞 25%        | 입력 앞 25%에서 약 1,024개를 FPS로 선택, 나머지는 미선택 후보에서 순서대로 채움 | 입력 앞 25%에서 256개를 FPS로 선택, 나머지는 순서대로 채움 | 집계·평활화 모두 FPS-Prune 적용              |
| 캡슐 · 무작위 후보 25%   | 전체에서 무작위 25%를 뽑아 후보로 사용. 직접 선택 수와 순서 채우기는 유지        | 집계와 같이 후보만 무작위 25%로 변경                 | 후보의 **수는 그대로**, 뽑는 위치만 변경           |
| 캡슐 · 직접 2,048개    | 같은 무작위 후보에서 직접 2,048개 + 순서 채움 2,048개                | 무작위 후보 25%에서 직접 256개 + 순서 채움           | 집계 단계에서 FPS 반복만 늘림                  |
| 캡슐 · 직접 4,096개    | 같은 무작위 후보에서 4,096개 전부 FPS로 선택                       | 직전과 동일                                 | 집계의 순서 채우기를 없앰. 후보 축소는 유지           |
| 캡슐 · 무작위 채움       | 직접 고른 2,048개 유지 + 미선택 후보에서 나머지 2,048개를 무작위로 채움      | 직접 2,048개 순서 채움 실험과 동일                 | 4,096개 실험이 아니라 **2,048개 순서 채움**과 비교 |
| 캡슐 · 평활화 원복       | 직접 2,048개 + 순서 채움 2,048개 유지                         | 전체 점군에서 기존 FPS로 1,024개 선택              | **평활화만 변경**, 집계 및 같은 정상 메모리뱅크 파일 유지 |
| **최종 · 52개 카테고리** | 무작위 후보 25%(시드 42)에서 직접 2,048개 + 순서 채움 2,048개        | 전체 점군에서 기존 FPS로 1,024개 선택              | 캡슐 평활화 원복 설정을 전체 범주에 적용하고 G도 다시 측정  |

- **논문과의 관계:** 최종판은 후보와 반복을 줄이는 **FPS-Prune의 변형**임. 집계 후보는 75% 줄였지만 직접 FPS 반복은 50%만 줄였고, 남은 중심점은 미선택 후보의 인덱스 순으로 채움. **FPS-Cache는 어느 행에도 적용하지 않음.** [FlashFPS 논문](https://arxiv.org/html/2604.17720)
- 표의 ‘바로 앞에서 확인한 변경’은 변경 요인을 뜻함. 4,096개·무작위 채움·평활화 원복은 모두 2,048개 순서 채움을 기준으로 나눈 실험이며, 변경을 순서대로 누적한 것이 아님.

## 4. 비교 조건과 해석 범위

| 비교 | 통제한 조건 | 결과를 해석할 때 주의할 점 |
|---|---|---|
| 캡슐 FPS 변형 | MiniShift 캡슐 원본 50만 점, 정상 54개·테스트 130개, 동일한 GPU KD-tree와 이웃 수 유지 | 집계 중심점이 바뀐 실험은 메모리뱅크를 새로 구성함. 평활화 원복만 기존 2,048개 뱅크를 그대로 사용함. 측정 시점이 달라 전체 시간 차이를 한 연산의 효과로 단정하지 않음 |
| 52개 최종 비교 | RTX 5080, MiniShift 12개와 Anomaly-ShapeNet 40개. 카테고리별 동일 입력·정답·원본 해상도, 같은 설정으로 두 버전을 다시 실행하고 실행 순서를 번갈아 적용함 | 각 버전의 정상 메모리뱅크를 따로 구성함. 카테고리 평균은 동일 가중치. 동일 시드·버전당 1회 결과이며 반복 실행 분산은 측정하지 않음 |

전체 추론 시간은 **특징 추출 + 점수 계산**이며, 파일 읽기·저장·평가지표 계산은 제외함. 최종 혼합판은 G 대비 추론 시간이 MiniShift에서 **24.3%**, Anomaly-ShapeNet에서 **21.8%** 줄었지만, 물체 AUROC는 각각 **1.88%p**, **0.20%p** 낮아졌음. 포인트 AUROC는 각각 **1.14%p**, **0.46%p** 높아졌음. 이 결과는 **같은 GPU KD-tree 위에서 집계 FPS만 바꾼 결과**이지, GPU KD-tree를 FlashFPS로 대체한 결과가 아님.

## 5. M2 — 대표점 4,096개 × 이웃 128개의 한계

**기준 단계:** 대표점의 위치는 이미 정해졌다고 가정함. 그다음 ① 원본 점군에서 대표점마다 정확한 128개 이웃을 찾고, ② 해당 점의 132차원 FPFH 특징을 가져와, ③ 평균을 내어 대표점당 특징 하나를 만드는 구간임. **대표점 선택(FPS)과 FPFH 계산 자체는 이 구간에 포함하지 않음.**

| 비교 근거 | 관찰 | M2에서 말할 수 있는 것 |
|---|---|---|
| 캡슐, 공식 호환판 → 전체 GPU KD-tree판 | 집계용 128-NN 조회 **14,606.10 → 31.90ms**. 공식 호환판 수치는 4,000개·96개 조회 두 번을 합친 값임 | 이웃 조회는 공식 호환판에서 큰 병목이었고, GPU KD-tree판에서는 훨씬 작아졌음. 전체 버전 간 비교이므로 배치·데이터 이동을 통제한 커널 단독 비교는 아님 |
| MiniShift 12개, 최종 혼합판 | 집계 128-NN **47.29ms**, 특징 가져오기 **0.62ms**, 전체 추론 **2,262.41ms**. FPFH용 전체 120-NN은 **1,254.35ms** | 집계 구간 안에서는 **128-NN 조회**가 먼저 줄일 대상임. 그러나 조회만 완전히 없애도, 다른 비용이 그대로라는 가정에서 전체 추론 절감 상한은 약 **2.1%**임. 특징 평균의 단독 시간은 기존 집계에서 분리되지 않음 |
| 캡슐, 이웃 128 → 16 | 집계 조회 **31.90 → 7.04ms**, 포인트 AUROC **80.75 → 78.20%**, 포인트 AP **22.77 → 20.93%** | 이웃을 줄이면 조회는 빨라지지만 **같은 특징을 만드는 최적화가 아님**. 단일 범주 결과로 128개가 항상 최적이라고 결론 내리지는 않음 |

**원인 가설 1 — 조회 중복.** 대표점 4,096개는 원본 점군에서 뽑은 점임. 그런데 FPFH용으로 원본 각 점의 가까운 120개를 이미 조회한 뒤, 집계 단계에서 대표점마다 다시 128개를 찾음. 현재 120개 목록만으로는 정확한 128개를 복원할 수 없지만, 두 조회의 결과가 상당 부분 겹칠 가능성이 있음. 동점과 자기 자신 포함 규칙까지 같은지는 검증 필요.

**원인 가설 2 — 평균을 내기 전 큰 임시 텐서 생성.** 현재 코드는 이웃 특징을 모두 펼쳐 `4,096 × 128 × 132` FP32 텐서를 만든 뒤 평균냄. 이 중간 텐서의 이론 크기는 **264MiB/샘플**이지만, 측정된 전체 VRAM 증가량이나 실제 메모리 이동량을 뜻하지는 않음. 가져오기 시간이 작았으므로 이 문제는 우선 **메모리 개선 후보**이지, 큰 속도 향상의 근거는 아님.

## 6. M3 — 128개를 유지하면서 집계 비용을 줄이는 방법

| 참고 연구 | 가져올 원리 | Simple3D에서의 적용과 한계 |
|---|---|---|
| [FastPoint, ICCV 2025 §4.2](https://openaccess.thecvf.com/content/ICCV2025/papers/Lee_FastPoint_Accelerating_3D_Point_Cloud_Model_Inference_via_Sample_Point_ICCV_2025_paper.pdf) | 샘플링 중 계산한 거리 정보를 다음 이웃 탐색에 재사용함 | **앞 단계의 공간 정보를 재사용한다는 원리만** 가져옴. 여기서는 FPS 정보가 아니라 FPFH용 이웃 목록을 재사용하며, FastPoint의 탐색 방향·알고리즘을 그대로 이식하는 것이 아님 |
| [Jakob·Guthe, Computer Graphics Forum 2021 §5.3](https://doi.org/10.1111/cgf.14177) | 정확한 GPU k-NN에서 트리 순회와 후보 관리 방식을 최적화함 | 재사용으로 이득이 없을 때 비교할 탐색 후보임. 논문 구현은 실험 장비에서 k=114 초과 결과를 제시하지 못했으므로 **k=128에 바로 쓸 수 있다는 근거는 아님** |
| [TorchSparse, MLSys 2022 §4.3.2](https://proceedings.mlsys.org/paper_files/paper/2022/file/c48e820389ae2420c1ad9d5856e1e41c-Paper.pdf) | 중간 데이터를 따로 저장하는 비용을 줄이고 메모리 접근을 합침 | 같은 128개 인덱스에서 특징을 읽자마자 채널별로 합산하는 **gather–mean 결합**에 착안함.  |

### 제안 A — 앞에서 찾은 이웃 목록을 집계에도 재사용

현재 GPU KD-tree의 **전체 120-NN 조회 + 대표점 128-NN 조회**를 **전체 128-NN 조회 한 번 + 대표점 인덱스로 해당 행 읽기**와 비교함. FPFH는 기존처럼 앞 40·80·120개만 사용하고, 집계는 해당 대표점의 128개를 모두 사용함. FPS가 이미 반환하는 원본 인덱스를 보존하면 같은 좌표를 다시 검색할 필요가 없음. 점수 평활화 12-NN과 FPS는 그대로 둠.

### 제안 B — 이웃 특징을 가져오면서 바로 평균

128-NN 인덱스는 기존과 동일하게 사용하되, 큰 텐서를 따로 저장하지 않고 특징을 읽으면서 합산한 뒤 128로 나눔. 최종 출력은 기존과 같은 `4,096 × 132`임. 기대 효과는 **임시 메모리 감소**이며, FPS나 k-NN을 바꾸는 방법은 아님. FP32 합산 순서 때문에 작은 수치 차이가 날 수 있어 출력과 최종 점수를 대조함.

### 캡슐에서 검증한 결과

- **A · 전체 128-NN 재사용 — 미채택.** 대표점 조회/목록 읽기는 32.69 → 0.24ms였으나, 50만 점 전부에서 이웃을 8개 더 찾는 비용이 더 컸음. 두 조회 합계는 1,156.56 → 1,275.90ms, 평균 추론은 **5.4% 증가**. 탐지 지표는 같았음. 캡슐 재사용 실험 (로컬 기록: `W47_Simple3D_capsule_GPU_KDTree_FlashFPS_reuse128_comparison.md`)
- **B · 읽으면서 평균 — 집계 메모리 절감은 확인, 전체 최적화로는 보류.** 집계 구간의 PyTorch 요청 할당량은 **266.06 → 2.06MiB**였으나 전체 최대 PyTorch 할당은 4.77GiB로 같았음. 집계 자체는 0.913 → 0.403ms로 줄었지만, 단일 측정에서 전체 평균은 소폭 단축되고 p95는 증가했으므로 전체 속도 개선으로 결론 내리지 않음. 캡슐 결합 평균 실험 (로컬 기록: `W47_Simple3D_capsule_FlashFPS_fused_gather_mean.md`)

| 목표 | 찾아볼 방법 | Simple3D에서 바꿀 부분과 확인할 점 |
|---|---|---|
| **M3 우선: 같은 128개 이웃을 더 빠르게 찾기** | **공간적으로 가까운 조회를 묶는 정확한 GPU k-NN**. [ArborX §2.2.3](https://dalg24.github.io/files/2020-paper-toms-arborx.pdf)의 Morton 순서 참고 | 같은 대표점 4,096개를 조회 직전에만 공간순으로 정렬하고, 같은 KD-tree로 정확한 128-NN을 찾은 뒤 결과 행을 원래 대표점 순서로 되돌림. 가까운 대표점이 트리의 비슷한 가지를 탐색한다는 가설임. **정렬 + 조회 + 복원** 합계가 기존 조회보다 짧아야 함. 논문의 효과가 현재 CuPy KD-tree에도 나오는지는 미확인 |
| **M3 후속: 대표점의 중복 조회 없애기** | **대표점만 128-NN, 나머지는 120-NN으로 나누는 선택적 재사용** | 좌표만 사용하는 FlashFPS를 먼저 실행해 대표점을 정함. 대표점 4,096개는 128개를 한 번 찾아 FPFH와 집계에 공유하고, 나머지 점은 기존처럼 120개만 찾음. 전체 128-NN을 돌린 A와 다름. 두 묶음의 조회·분리·재배치 시간까지 합쳐 기준보다 빠른지 확인함 |
| **전체 추론을 더 크게 줄이기** | **FPFH용 전체 120-NN의 조회 순서 최적화**, 또는 **보간에서 전체 정렬 대신 가까운 3개만 선택**. [GPU k-selection 연구](https://arxiv.org/abs/1702.08734) 참고 | 캡슐에서 집계용 128-NN은 약 34ms, FPFH용 전체 120-NN은 약 1,162ms, 두 점수 보간 합계는 약 299ms였음. 전체 속도가 목표라면 이 두 구간을 별도로 조사함. 보간은 거리 동점 처리와 점수 차이를 확인함 |
