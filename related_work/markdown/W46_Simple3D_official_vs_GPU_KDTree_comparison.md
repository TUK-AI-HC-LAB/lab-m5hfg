# W46 Simple3D 공식 호환판과 GPU KD-tree 결과 비교

## 1. 비교 대상과 집계 기준

- **새 비교 측정 104/104개 완료·검증됨.** Anomaly-ShapeNet 40개, MiniShift 12개를 두 버전으로 각각 실행함.
- 이번 문서는 동일 측정 도구로 새로 얻은 공식 호환판과 GPU KD-tree판 결과를 비교함. [이전 KD-tree 단독 결과](W46_Simple3D_GPU_KDTree_results_only_20261104.md)와 수치를 섞지 않음.
- **공식 호환판(O)**: 누락 import·데이터/정답 경로·CPU/GPU 인덱스 장치 오류만 보완한 공식 알고리즘. CPU Open3D FPFH, native CUDA FPS/KNN_CUDA, 공식 full-sort 보간, torch.cdist/min 유지함.
- **GPU KD-tree판(G)**: 같은 공식 호환판을 기준으로 CuPy GPU KD-tree 및 별도 CUDA FPFH 경로 적용함. 두 버전 모두 CPU 점수맵과 CPU 인덱스를 사용함. 이전 단독 실행의 GPU 점수맵 반환 우회와 구분됨.
- 공통 설정: RTX 5080, Python 3.11, Torch 2.11/CUDA 12.8, Open3D 0.20, 스레드 4개, num_group=4096, group_size=128, max_nn=40, MSND/LFSA 활성화, num_MSND=2, coreset 5%. 저자 구형 실행 환경과 동일하지 않음.
- 원본 해상도, 같은 입력 목록/순서/정답 사용함. 각 버전에서 새 메모리뱅크와 점수 생성함. 카테고리마다 두 버전의 실행 순서를 교대함.
- 단일 실행 결과이며 반복 실행에 따른 분산·통계적 유의성을 측정한 것은 아님.

### 표 읽는 법

- O=공식 호환판, G=GPU KD-tree판.
- 차이 열·행의 이름은 G-O이며, 계산은 G 값−O 값임. 정확도는 **%p**, 속도 배수=O 시간÷G 시간. 1배보다 크면 G가 빠름.
- 모든 **G-O** 열·행은 같은 계산 방향을 사용함. `−`는 G가 O보다 작고, `+`는 큼을 뜻함. 시간·메모리·전력은 표의 단위, GPU 사용률·정확도 차이는 %p, 온도 차이는 °C 단위임.
- G-O는 반올림 전 원시값으로 계산함. 따라서 화면에 표시된 O/G 값을 뺀 값과 끝자리 차이가 날 수 있음. 비교할 수 없는 `—` 항목은 차이도 `—`로 표시함.
- 정확도는 높을수록 좋고 시간은 낮을수록 빠름. 평균 추론=특징 추출+점수 처리이며 입력 읽기·저장·지표 계산 제외함.
- GB는 10⁹ bytes임. 데이터셋 평균 성능·시간은 카테고리를 동일 가중치로 평균함. 카테고리별 p95를 평균해 전체 p95로 보고하지 않음.
- 시간은 계측 래퍼·이벤트 기록 비용을 포함한 값임. 순수 무계측 지연과 동일하다고 주장하지 않음.

## 5. 결과 해석과 비교 한계

- GPU KD-tree판은 두 데이터셋 모두 평균 추론과 메모리뱅크 구성 시간이 짧았음. 다만 **정확도가 완전히 같지는 않음**.
- 가장 큰 포인트 AUROC 하락은 MiniShift screw에서 -0.92%p였음.
- G는 KD-tree만 바꾼 것이 아니라 FPFH 연산 경로·Float32 계산·k120 조회 재사용 등도 함께 바꾼 구현임. 속도 차이를 KD-tree 하나만의 효과로 해석할 수 없음.
- 전체 VRAM은 GPU 전체 표본 값이므로 화면 출력·다른 앱 사용량을 포함함. Torch 최대 할당은 CuPy/KD-tree 등 외부 할당을 제외함. 둘의 차이를 곧바로 KD-tree 메모리 크기로 해석할 수 없음.
- GPU 사용률은 작업량의 정밀한 계수나 SM 점유율이 아님. 사용률이 높다는 이유만으로 더 효율적이라고 판단할 수 없음.
- 자원 측정 간격은 목표 0.5초에 조회 지연이 더해짐. 더 짧은 피크를 놓칠 수 있으며, 짧은 개별 단계의 전력·사용률을 독립 측정한 것은 아님. 평균 전력을 전체 실행 시간과 곱해 실제 소비 에너지로 보고하지 않음.
- 단계별 표는 계측 가능한 공개 호출 단위임. CPU FPFH 내부 하위 연산과 모든 개별 CPU↔GPU 복사·커널을 전부 분리한 표는 아님.

## 7. 실제 코드 변경 내역

**이 표의 G는 FPFH만 GPU로 바꾼 버전이 아님. 중심점 주변 128개 이웃과 점수 평활화용 12개 이웃 탐색도 GPU KD-tree로 교체한 버전임.** 해당 변경까지 포함한 상태로 측정된 결과이므로, 속도 차이를 FPFH 가속만의 효과로 해석할 수 없음. 이 절은 이미 실행한 변경을 기록한 것이며 추가 코드 수정이나 재실행을 뜻하지 않음.

### 7.2 GPU KD-tree판에만 적용한 연산 변경

별도 [simple3d_gpu_kdtree.py](../../method12/source/simple3d_gpu_kdtree.py)의 `install()`을 호출해 실행 중 해당 함수·모듈 참조를 교체함. 공식 호환판 O에는 이 backend를 설치하지 않음. 공식 실행본의 FPFH 파일 자체를 GPU 구현으로 덮어쓴 것은 아님.

| 항목                | O: 공식 호환판                                                           | G: GPU KD-tree판                                      | 변경 코드·함수                                                                     |
| ----------------- | ------------------------------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------- |
| FPFH 실행 장치·구현     | Open3D legacy CPU `compute_fpfh_feature()` 호출                       | Open3D 수식을 참고해 작성한 별도 CUDA SPFH·FPFH 커널 사용           | `get_features()`, `descriptors()` 및 `simple3d_gpu_kdtree.cu`의 `spfh`, `fpfh` |
| FPFH 주변 이웃 탐색     | Open3D CPU FPFH 호출 내부에서 이웃 탐색                                       | GPU에 `cupyx.scipy.spatial.KDTree`를 만들고 이웃 조회         | `get_features()`의 `KDTree(xyz)`                                              |
| 40·80·120개 이웃 준비  | 스케일별 FPFH 호출에서 이웃 탐색 수행                                             | 전체 점에 대해 120개 이웃을 한 번 조회하고 앞 40·80·120개를 각 스케일에서 재사용 | `all_neighbors()`, `descriptors(..., k)`                                     |
| 탐색 반경 처리          | FPFH 반경 1,000,000 안에서 최대 이웃 수 제한                                    | 반경 제한 없는 정확 kNN 조회 사용. 입력 범위가 원래 큰 반경보다 작다는 조건을 검사함  | 입력 대각선 길이 검사, `tree.query(..., eps=0, p=2)`                                  |
| 계산 정밀도            | CPU Open3D 계산 결과를 Float32로 바꿔 GPU에 전달                               | 좌표·법선을 Float32로 올리고 SPFH·FPFH도 Float32로 계산           | `cp.asarray(..., dtype=cp.float32)`, CUDA 커널의 `float`                        |
| FPFH 데이터 이동       | CPU에서 계산한 각 스케일 특징을 GPU로 이동                                         | CPU 좌표·법선을 GPU로 옮긴 뒤 GPU에서 스케일 특징 생성                 | `positions_normals_upload`, `descriptors()`                                  |
| CuPy와 PyTorch 연결  | CuPy 경로 없음                                                          | DLPack으로 GPU 배열·텐서를 연결해 동일 메모리를 공유                   | `torch_view()`, `torch.utils.dlpack.from_dlpack()`                           |
| 스케일 특징 연결         | 40·80을 연결한 중간 결과를 만들고 80·120을 다시 연결                                 | 40·80·80·120을 한 번의 `torch.cat()`으로 연결                | `concatenate` 함수. 결과 132차원과 중복 80 스케일은 유지                                    |
| 특징 집계용 128개 이웃 탐색 | native GPU `KNN_CUDA` 사용                                            | FPFH에 사용한 GPU KD-tree로 중심점의 128개 이웃 조회               | `get_features()`의 `TreeKNN(self.args.group_size)`                            |
| 중심점 조회 배치         | `batched_knn(..., batch_size=4000)`으로 중심점 4,096개를 4,000+96개로 나눠 처리  | 중심점 4,096개를 한 번의 KD-tree 조회로 처리                      | `TreeKNN.__call__()`                                                         |
| 점수 평활화용 12개 이웃 탐색 | `Features.compute_anomay_scores()`에서 native GPU `KNN_CUDA(k=12)` 사용 | 같은 호출 위치에서 `TreeKNN(k=12)` 사용                        | `run.base.features_module.KNN = TreeKNN`                                     |
| GPU 탐색 구조 재사용     | FPFH 내부 탐색과 중심점 KNN_CUDA 경로가 분리됨                                    | 한 입력 점군에서 만든 트리를 FPFH·128개 이웃·12개 이웃 조회에 재사용         | `CACHE['tree']`, `CACHE['dense_ptr']`. 새 입력마다 캐시 초기화                         |
| 라이브러리 간 동기화       | PyTorch·CPU Open3D 중심 실행                                            | CuPy와 PyTorch가 서로의 결과를 읽기 전 필요한 동기화 추가               | `sync()`, `torch_view()`, `TreeKNN.__call__()`                               |
| 입력·재사용 검증         | 기존 경로 사용                                                            | 입력 형상·점 수·범위를 확인하고, 재사용할 트리가 현재 GPU 좌표와 같은지 포인터 검사   | `get_features()`의 입력 검사, `TreeKNN.__call__()`의 `data_ptr()` 검사               |

CUDA FPFH는 점마다 GPU 스레드를 배정하고 33차원 SPFH를 계산한 뒤 이웃의 SPFH를 모아 FPFH를 계산함. 스케일 40·80·120마다 계산하며, 이웃 목록만 공유함. CUDA 커널은 `--fmad=false`로 컴파일하지만 CPU 계산과 bitwise 동일함을 보장하지 않음. Float32·이웃 순서·히스토그램 경계 등의 차이로 수치가 달라질 수 있음.

실제 실행 중 교체한 핵심 참조는 다음 두 가지임.

```python
run.base.FPFHFeatures.get_fpfh_features = get_features
run.base.features_module.KNN = TreeKNN
```

두 번째 참조 교체 때문에 **FPFH 바깥의 12개 이웃 탐색까지 변경됨**. 또한 첫 번째로 교체한 특징 추출 함수 안에서 128개 이웃 탐색을 직접 `TreeKNN`으로 호출함. 따라서 중심점 이웃 탐색이 공식 `KNN_CUDA` 그대로인 실험이 아님.

- CUDA 계산 코드: [simple3d_gpu_kdtree.cu](../../method12/source/simple3d_gpu_kdtree.cu).
- 적용 위치: [측정 worker](../../method12/source/compare_simple3d_worker.py)의 `mode == 'gpu_kdtree'` 조건에서 `backend.install(..., detail_tracing=True)` 호출.

### 7.3 교체하지 않은 주요 연산

| 항목 | 유지 내용 |
|---|---|
| 법선 계산 | CPU Open3D, 반경 10,000·최대 이웃 10개 유지 |
| FPS·FPS 결과 모으기 | native PointNet2 CUDA 연산과 중심점 수 유지 |
| LFSA | 중심점 이웃 특징을 평균하는 방식 유지. 단, 이웃을 찾는 구현은 위 표처럼 변경됨 |
| 특징 연결 결과 | 40·80·80·120 스케일, 132차원 유지 |
| coreset | 공식 선택 방식과 5% 비율 유지 |
| 메모리뱅크 NN | GPU `torch.cdist()`와 최소 거리 선택 유지. FAISS로 바꾸지 않음 |
| 점수 보간 | 공식 full-sort 구현 유지. TopK 보간으로 바꾸지 않음 |
| 이미지 점수 | 상위 80개 포인트 점수 평균 유지 |
| 데이터 | 같은 원본 점군·해상도·정답·순서 유지 |
