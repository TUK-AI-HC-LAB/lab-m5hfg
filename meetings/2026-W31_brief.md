- 목적: 대표 정상 조각을 `10%` 대신 `1%`만 남겨도 성능이 유지되는지 확인함.

- 현재 상태: 2026-07-27 기준 15개 종류 전체 실행 완료.
- 결과 저장: [10%·1% 비교 CSV](../method1/source/results/PatchCore_MVTecAD_IM224_WR50_coreset_comparison.csv)
- 평균 결과: 대표 정상 조각을 10%에서 1%로 줄이면 image AUROC는 `0.9910 → 0.9896`, pixel AUROC는 `0.9812 → 0.9798`로 각각 약 `0.14%p` 낮아짐.

## 1. PatchCore를 쉬운 말로 설명하면

### 1.1 풀려는 문제

공장에서 나온 제품 사진을 보고 흠집, 오염, 파손 같은 이상을 찾는 문제입니다. 학습할 때는 주로 정상 제품 사진만 사용합니다. 그러므로 모델은 “정상 제품은 보통 어떻게 생겼는가”를 먼저 익히고, 정상과 많이 다른 부분을 이상으로 표시합니다.

### 1.2 PatchCore의 핵심 아이디어

1. 정상 제품 사진을 작은 조각으로 나눠 봅니다.
2. 각 조각의 모양과 질감을 숫자 묶음으로 바꿉니다.
3. 정상 조각의 숫자 묶음을 저장합니다.
4. 새 사진의 조각이 저장된 정상 조각들과 얼마나 다른지 비교합니다.
5. 가장 많이 다른 조각이 있으면 이상 가능성이 높다고 판단합니다.

예를 들어 정상 병 사진에는 매끈한 표면 조각이 많이 저장됩니다. 테스트 병 사진에 흠집 조각이 있으면, 저장된 매끈한 조각들과 거리가 멀어져 이상 점수가 높아집니다.

### 1.3 꼭 알아야 하는 용어

| 용어 | 쉬운 뜻 |
|---|---|
| patch(패치) | 사진을 나눈 작은 조각 |
| 특징(feature) | 조각의 모양·색·질감을 숫자로 나타낸 값 |
| normal memory(정상 메모리) | 정상 사진 조각의 특징을 모아 둔 목록 |
| coreset(코어셋) | 정상 메모리가 너무 커지지 않도록, 중요한 대표 조각만 남긴 목록 |
| 최근접 거리 | 테스트 조각과 가장 비슷한 정상 조각 사이의 차이. 클수록 더 낯선 조각이라는 뜻 |
| AUROC | 정상과 이상을 구분하는 점수. 1에 가까울수록 잘 구분함 |
| image AUROC | 사진 전체가 정상인지 이상인지 구분하는 점수 |
| pixel AUROC | 사진 속 어느 위치가 이상인지 찾는 점수 |
| baseline(기준 실험) | 이후 실험과 비교하기 위해 먼저 실행하는 기본 설정 |

## 3. 실행 중 있었던 문제와 처리

### 문제

Windows에서 정상 메모리를 검색할 때 한 번에 너무 많은 조각을 비교하면 컴퓨터 메모리가 부족하다는 오류가 발생했습니다.

### 처리

검색할 조각을 한꺼번에 보내지 않고, 128개씩 나누어 보냈습니다. 변경 내용은 [Windows 호환 patch](../method1/source/patchcore_windows_compat.patch)에 기록했습니다.

### 의미와 한계

- 바뀐 것은 한 번에 처리하는 양뿐입니다. 어떤 거리를 쓰는지, 어떤 정상 조각을 가장 가깝다고 고르는지는 바꾸지 않았습니다.
- 따라서 같은 방식의 검색을 더 안전하게 실행한 것입니다.
- 다만 원본 코드를 아무 수정 없이 실행한 결과는 아니므로, 문서와 발표에서 이 사실을 함께 밝혀야 합니다.

### 4.2 논문과 비교한 해석

논문의 같은 기본 설정은 사진 전체 구분 점수 `0.9920`, 이상 위치 찾기 점수 `0.9810`입니다 [1]. 이번 결과는 각각 `0.9910`, `0.9812`입니다.

차이가 매우 작으므로, 현재 환경에서도 PatchCore가 논문과 비슷하게 작동했다고 판단할 수 있습니다. 다만 컴퓨터 환경과 검색 처리 방식이 완전히 같지는 않으므로, 결과가 완전히 똑같다고 말할 수는 없습니다.

### 4.3 대표 정상 조각을 줄인 결과: 10% 대 1%

| 비교 항목 | 10% 사용 | 1% 사용 | 변화 |
|---|---:|---:|---:|
| 사진 전체 구분 점수 | 0.9910 | 0.9896 | -0.0014 |
| 이상 위치 찾기 점수 | 0.9812 | 0.9798 | -0.0014 |

정상 조각을 10분의 1만 남겨도 평균 점수는 약 `0.14%p`만 낮아졌습니다. 즉, 대표 조각을 크게 줄여도 이번 설정에서는 성능이 크게 무너지지 않았습니다. 다만 실행 시간과 실제 메모리 사용량은 이전 10% 실험에서 같은 방식으로 기록하지 않아 공정하게 비교할 수 없습니다.

### 4.5 히트맵 시각화와 사례 분석

- 대상: `bottle`, `pill`, `transistor`.
- 이유: `bottle`은 높은 점수의 기준 사례이고, `pill`과 `transistor`는 상대적으로 낮은 위치 찾기 점수를 보인 사례임.
- 만든 자료: 원본 사진, 정답 이상 위치, PatchCore가 계산한 이상 히트맵을 한 장에 표시한 이미지.
- 대표 이미지: [bottle](../method1/source/results/patchcore_visualizations/bottle/bottle_test_broken_large_000.png), [pill](../method1/source/results/patchcore_visualizations/pill/pill_test_color_000.png), [transistor](../method1/source/results/patchcore_visualizations/transistor/transistor_test_bent_lead_000.png)
- 생성 수: `bottle` 83장, `pill` 167장, `transistor` 100장.

| 사례 | 관찰 | 해석 |
|---|---|---|
| bottle / broken_large | 실제 파손 부분 주변에 높은 이상 점수가 모임 | 정상 병 표면과 다른 모양을 잘 찾은 기준 사례 |
| pill / color | 작은 색 점 결함 주변에 점수가 높지만, 다른 표면 점에도 반응함 | 작은 점 형태와 제품 표면 질감을 구분하기 어려워 pixel AUROC가 상대적으로 낮을 수 있음 |
| transistor / bent_lead | 휘어진 다리 끝부분에 높은 점수가 모임 | 모양이 변한 부품 끝을 위치 수준에서 잘 찾음 |

이 관찰은 각 사례의 히트맵을 눈으로 확인한 결과입니다. 모든 이미지의 오류 원인을 일반화한 결론은 아닙니다.

### 4.6 PatchCore 핵심 흐름 작은 직접 구현

- 파일: [patchcore_tiny_demo.py](../method1/source/patchcore_tiny_demo.py)
- 범위: 이미지 특징 추출기는 생략하고, 이미 얻은 숫자 특징을 사용해 대표 normal memory 선택과 최근접 거리 점수 계산을 직접 구현함.
- 구현한 과정: farthest-first 방식의 coreset 선택 → 테스트 patch와 normal memory의 거리 계산 → 가장 먼 patch 선택.
- 실행 확인: 정상 무리와 먼 세 번째 테스트 patch가 이상 후보로 가장 높은 점수 `1.562`를 받음.
- 주의: 이 파일은 원리를 배우기 위한 작은 예제이며, CNN 특징 추출·점수 재가중·실제 MVTec AD 평가까지 포함한 공식 PatchCore 구현체를 대체하지 않음.

## 5. 이번 결과로 알 수 있는 점과 아직 모르는 점

### 알 수 있는 점

- PatchCore 공식 기본 설정이 현재 환경에서 잘 실행됨.
- 15개 종류의 평균 성능이 논문의 예시와 매우 비슷함.
- 정상 조각 목록과의 차이로 이상을 찾는 방법이 실제 코드에서도 동작함.

### 아직 모르는 점

- 대표 정상 조각을 1%로 줄인 결과는 확보했지만, 다른 비율에서 성능이 어떻게 변하는지는 아직 모름.
- 입력 사진 크기나 특징 추출기를 바꾸면 결과와 실행 시간이 어떻게 달라지는지 모름.
- 논문 저자가 사용한 원래 컴퓨터 환경과 완전히 같은 결과인지 확인하지 못함.

## 6. 다음 실험 제안

정상 메모리에 남기는 대표 조각 비율을 `10%`와 `1%`로 비교했습니다. 원본 결과와 평균은 [comparison CSV](../method1/source/results/PatchCore_MVTecAD_IM224_WR50_coreset_comparison.csv)에 저장했습니다.

| 비교할 항목 | 확인하려는 이유 |
|---|---|
| AUROC 점수 | 대표 조각을 줄여도 이상을 잘 찾는지 확인 |
| 실행 시간 | 이번 비교에서는 공정하게 기록하지 못했으므로 다음 실행에서 함께 기록 |
| 정상 메모리 크기 | 비율상 10%에서 1%로 90% 줄었지만, 실제 사용량은 다음 실행에서 기록 필요 |
| 종류별 점수 | 어떤 제품 종류에서 성능이 많이 달라지는지 확인 |

성능 비교, 시각화, 기본 사례 분석, 작은 직접 구현까지 완료했습니다. 다음 실험에서는 coreset 비율별 실행 시간과 실제 memory 사용량을 같은 방식으로 기록해야 합니다.
