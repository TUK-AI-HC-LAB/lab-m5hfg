W40 교수님 설명 스크립트
주제: 공통 이상 탐지 프레임워크의 정상 validation 분할과 전체 method 재실행

0. 먼저 결론부터 말씀드리겠습니다.

이번 주에는 새로운 이상 탐지 모델을 제안한 것이 아닙니다.
여러 방법을 하나의 공통 실행 구조에서 돌릴 때, 기존에는 학습용 정상 이미지 209장을 모두 TRAIN으로 사용하고 validation은 사실상 비어 있던 문제를 수정했습니다.

수정 뒤에는 MVTec AD bottle의 정상 train 이미지 209장을
  - TRAIN 188장
  - VAL 21장
으로 나누고,
  - TEST는 기존 83장(정상 20장, 실제 결함 63장)
그대로 유지했습니다.

그 다음 PatchCore, PaDiM, WinCLIP 등 12개 등록 방법을 같은 bottle, 같은 seed 0, 같은 각 방법의 기본 config로 다시 실행했습니다.
결과적으로 GLASS를 제외한 11개 방법은 모두 CSV까지 생성했습니다.
GLASS의 실패 원인은 validation 수정이 아니라, 가짜 결함을 만들 때 필요한 DTD 텍스처 데이터가 PC에 없었기 때문입니다.

중요한 해석은 다음과 같습니다.
  - SimpleNet을 제외한 10개 완료 방법은 bottle 한 클래스, seed 하나에서 Image AUROC가 거의 변하지 않았습니다.
  - SimpleNet은 Image AUROC 0.9944에서 0.9151로, Pixel AUROC 0.8776에서 0.6742로 낮아졌습니다.
  - 하지만 이것만으로 'SimpleNet이 validation 분할에 약하다'고 결론 내리지는 않습니다.
    bottle 하나와 seed 하나만 본 관찰이기 때문입니다.


1. 왜 공통 프레임워크를 만들고 분석했는지 설명드리겠습니다.

이상 탐지 방법은 내부 원리가 서로 다릅니다.

  - PatchCore는 정상 이미지의 patch feature를 많이 저장해 놓고, test patch가 가장 가까운 정상 patch에서 얼마나 먼지로 이상을 판단합니다.
  - PaDiM은 정상 feature가 어떤 분포를 이루는지 학습하고, test feature가 그 분포에서 얼마나 벗어나는지 봅니다.
  - SimpleNet은 정상 feature와 인위적으로 만든 가짜 이상 feature를 구분하는 discriminator를 학습합니다.
  - RD는 teacher feature를 decoder가 복원하지 못하는 차이로 이상을 찾습니다.
  - WinCLIP과 AnomalyCLIP은 CLIP의 text/image representation과 prompt를 이용합니다.

이렇게 내부 수식은 다르지만, 공통 framework는 아래의 바깥 흐름을 통일합니다.

  experiment YAML
    -> main.py가 설정을 읽음
    -> component_registry.py가 method 이름을 실제 Trainer class에 연결함
    -> main_dataset.py가 TRAIN/VAL/TEST DataLoader를 만듦
    -> main_net.py가 해당 Trainer를 생성함
    -> main_run.py가 train, test, metric, CSV 저장을 순서대로 실행함

예를 들어 YAML에서 method: patchcore라고 쓰면 PatchCore Trainer가 선택되고,
method: simple이라고 쓰면 SimpleNet Trainer가 선택됩니다.
runner는 PatchCore의 memory bank나 SimpleNet의 discriminator 내부를 직접 알 필요가 없습니다.
선택된 Trainer가 공통 입력과 공통 출력 형식을 지키면 됩니다.

여기서 공통 입력은 DataLoader가 주는 batch입니다.
  - image: 모델이 보는 RGB image tensor
  - mask: 결함 위치의 정답. 모델 입력이 아니라 pixel 성능 평가에만 사용함
  - is_anomaly: 정상 0, 이상 1인 이미지 정답 label
  - image_path: 원본 파일 경로

모델은 image만 보고 두 종류의 출력을 만듭니다.
  - image anomaly score: 사진 한 장이 이상인지 나타내는 숫자 하나
  - anomaly map: 사진 안의 위치별 이상 점수 지도

그 뒤 runner가 image score와 is_anomaly로 Image AUROC를 계산하고,
anomaly map과 mask로 Pixel AUROC, Saliency F1을 계산합니다.


2. 기존 코드에서 발견한 문제를 설명드리겠습니다.

MVTec AD의 폴더 구조에는 보통 validation 폴더가 없습니다.

  bottle/
    train/good/      정상 train 이미지 209장
    test/good/       정상 test 이미지 20장
    test/broken_*/   실제 결함 test 이미지 63장
    ground_truth/    결함 위치 mask

그런데 기존 공통 framework의 validation 분할 코드는 주석 처리되어 있었습니다.
또 VAL이 실제로 어느 폴더를 읽어야 하는지가 정상 train 이미지와 맞게 연결되어 있지 않았습니다.

따라서 기존 실행은 다음 구조였습니다.

  train/good 209장 -> TRAIN 209장
  VAL           -> 없음
  test 83장     -> 최종 평가

이 구조가 곧바로 잘못된 test는 아닙니다.
학습 209장과 test 83장은 서로 다른 파일이므로, 학습 이미지를 test에도 쓴 것은 아닙니다.

문제는 개발 과정입니다.
모델 A, B, C, D 중 어떤 config나 epoch가 나은지 여러 번 고르려 할 때 VAL이 없으면 사람이 test AUROC를 계속 보게 될 가능성이 큽니다.
그러면 test set이 '마지막 한 번만 보는 시험지'가 아니라, 간접적으로 설정을 고르는 기준이 될 수 있습니다.

그래서 validation을 만들었습니다.
다만 여기서 꼭 구분해야 할 것이 있습니다.

이번 VAL 21장은 정상 이미지만 있습니다.
따라서 '정상인데 이상이라고 과하게 점수를 주는가', 즉 normal false positive를 점검하는 데는 쓸 수 있습니다.
반대로 실제 결함을 얼마나 잘 찾는지까지 VAL만으로 판단할 수는 없습니다.
VAL에 실제 결함 mask가 없기 때문입니다.


3. 정확히 어떤 코드를 바꿨는지 설명드리겠습니다.

(1) datasets/base.py

Dataset이 받은 seed를 저장하도록 했습니다.
이 seed가 있어야 실행할 때마다 train/validation 이미지가 랜덤하게 바뀌지 않습니다.
이번 bottle experiment에서는 seed 0이므로, 다시 실행해도 같은 188장과 21장이 선택됩니다.

(2) datasets/mvtec.py

TRAIN과 VAL 모두 train/good에서 파일 목록을 읽도록 했습니다.
그 뒤 category 이름과 seed로 섞는 순서를 고정하고 90%/10%로 나눴습니다.

  TRAIN: 앞 188장
  VAL:   남은 21장

여기서 '앞'은 파일 시스템에서 우연히 나온 순서가 아니라, seed로 고정된 shuffle 뒤의 앞부분입니다.

TEST일 때만 test 폴더를 읽게 했습니다.
그래서 VAL이 test image나 test defect mask를 보지 않습니다.

(3) main_dataset.py

validation Dataset을 만들 때도 train_val_split=0.9를 전달했습니다.
이전에는 validation DataLoader를 만드는 부분이 있어도, 실제 데이터 분할 비율이 올바르게 전달되지 않았습니다.

(4) main.py

기본 train_val_split을 1.0에서 0.9로 바꿨습니다.

  - 0.9: 현재 기본값. 정상 train의 90%는 학습, 10%는 validation.
  - 1.0: 이전 실행을 완전히 재현하고 싶을 때. 209장을 모두 TRAIN에 사용하고 VAL은 비게 됨.

수정 직후에는 자동 검사도 했습니다.

  TRAIN ∩ VAL = 0
  VAL ∩ TEST = 0

즉, TRAIN의 188장과 VAL의 21장은 겹치지 않고,
VAL의 21장은 test 83장과도 겹치지 않았습니다.
PatchCore를 실제로 한 번 실행해 DataLoader가 188/21/83으로 만들어지고 CSV가 저장되는 것까지 확인했습니다.


4. validation을 만들었는데, 모델이 이미 이를 이용하고 있는지 설명드리겠습니다.

현재는 'validation DataLoader를 올바르게 생성하고 Trainer에 전달'하는 단계까지 완료했습니다.

공통 호출 형태는 다음과 같습니다.

  model.train(training_data, validation_data, test_data, dataset_name)

즉, Trainer는 validation_data를 받을 수 있습니다.
하지만 모든 Trainer가 이 값을 사용해
  - 가장 좋은 epoch를 자동으로 저장하거나,
  - early stopping을 하거나,
  - hyperparameter를 고르는
상태는 아직 아닙니다.

따라서 이번 실험은 'validation으로 선택한 모델이 더 좋아졌는가'를 보는 실험이 아닙니다.
정확한 실험 질문은 다음입니다.

  '기존에 209장의 정상 이미지로 학습했던 방법들이,
   정상 이미지 21장을 학습에서 빼고도 여전히 실행되는가?
   그리고 test 성능은 어느 정도 달라지는가?'

결과의 1차 해석은 다음과 같습니다.

첫째, SimpleNet 외 10개 완료 방법은 Image AUROC가 반올림 네 자리 기준으로 바뀌지 않았습니다.
즉, bottle에서는 정상 train 이미지 209장 중 21장을 빼더라도, 이 방법들의 이미지 단위 정상/결함 분리 순위가 거의 유지됐습니다.

둘째, Pixel AUROC와 F1은 소폭 변했습니다.
이는 image-level로 결함 사진을 구분하는 것과, 결함의 정확한 위치를 칠하는 것은 다른 난이도이기 때문입니다.
하지만 한 클래스와 한 seed만으로 이 변화가 의미 있는지 판단할 수 없습니다.

셋째, SimpleNet은 큰 하락을 보였습니다.
가능한 설명은 정상 학습 image 수가 줄어 feature 분포나 discriminator 학습이 달라졌다는 것입니다.
그러나 아직 이것은 가설입니다.
다른 seed나 다른 MVTec class에서도 같은 하락이 반복되는지 확인해야 원인이라고 말할 수 있습니다.


7. 이 결과로 말할 수 있는 것과 말할 수 없는 것을 구분하겠습니다.

[말할 수 있는 것]

1) 공통 framework의 MVTec loader는 정상 train에서 test와 겹치지 않는 validation set을 만들 수 있습니다.

2) validation 분할을 적용해도 GLASS를 제외한 11개 method는 bottle에서 학습/추론/metric/CSV 저장까지 실제로 끝났습니다.

3) 이번 조건에서는 SimpleNet이 다른 방법보다 학습 이미지 수 감소에 민감할 수 있다는 관찰이 나왔습니다.

[말할 수 없는 것]

1) validation 분할이 모든 방법의 성능을 좋게 하거나 나쁘게 만든다는 일반 결론.

2) SimpleNet 하락의 정확한 원인.
   현재는 bottle 한 개, seed 0 한 번이기 때문입니다.

3) 12개 방법의 공정한 성능 순위.
   각 방법의 backbone, image size, epoch, training 방식, prompt checkpoint가 다릅니다.
   특히 AnomalyCLIP은 ViSA에서 학습된 prompt checkpoint를 가져와 MVTec bottle에 평가했으므로,
   다른 normal-train 방법과 같은 출발 조건이라고 볼 수 없습니다.

4) MVTec AD 전체 15개 category에 대한 결론.
   bottle은 빠르게 코드 경로를 검증하기 위해 선택한 대표 category입니다.
   bottle이 특별히 전체 데이터셋을 대표해서 선택한 것은 아닙니다.


8. 다음 작업과 교수님께 받고 싶은 판단입니다.

다음에 바로 할 수 있는 작업은 두 개입니다.

첫 번째는 SimpleNet입니다.
SimpleNet 하락이 우연인지 확인하기 위해 다른 seed와 다른 MVTec category에서도
  209장 학습 vs 188장 학습
비교를 반복합니다.
이때 전체 15개 category를 한 번에 모두 돌리기보다, 먼저 bottle 외 2~3개 category와 seed를 추가해
하락 패턴이 반복되는지 확인하는 것이 비용 대비 적절하다고 판단합니다.

두 번째는 validation 활용입니다.
현재는 VAL을 만들었지만 Trainer가 그것으로 best epoch/checkpoint를 고르지 않습니다.
교수님께서 방향을 허용하신다면 다음 단계에서
  - 정상 VAL의 image anomaly score 분포를 계산하고,
  - 정상 false positive가 낮은 epoch/checkpoint를 저장하며,
  - 그 선택은 test metric을 보지 않고 수행하도록
각 Trainer에 공통 정책을 설계하겠습니다.

다만 normal-only VAL에는 실제 결함이 없으므로,
'정상 오탐이 낮은 checkpoint'가 '실제 결함 탐지가 가장 좋은 checkpoint'와 항상 같다고 주장하면 안 됩니다.
이 한계는 문서와 이후 코드 설계에 명확히 남기겠습니다.

교수님께 드릴 최종 질문은 하나입니다.

  '정상 validation을 먼저 분리한 뒤, 다음 단계에서 각 Trainer의 epoch 또는 hyperparameter 선택을
   validation 기반으로 통일하는 것이 적절한가?'입니다.

제 현재 판단은 적절하다는 것입니다.
이유는 test set을 여러 후보 중 선택 도구로 쓰지 않도록 막는 기본 장치가 되기 때문입니다.
다만 normal-only validation의 한계를 인정하고, SimpleNet의 민감도는 추가 seed/category 실험으로 먼저 확인하겠습니다.
